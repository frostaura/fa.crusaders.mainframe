# Device protocol contract

Neutral ground. Owned by neither the firmware nor the backend.

Two implementations have to agree on these bytes and cannot see each other's
source: C++ on an 8-bit micro and an ESP8266, and C# on the server. Under
`src/iot/` the .NET tests would have to reach into firmware; under
`src/backend/` the firmware would have to reach into .NET. So the fixtures live
here and both sides read them.

This is not decoration. The repository already shipped one ESP32 sketch and one
webhook sender that had never successfully talked to each other — each was
internally consistent, each was tested against its own assumptions, and the
mismatch was invisible until someone looked at a 401 nobody had noticed for
months. A shared corpus is the cheapest thing that would have caught it.

## Families

| Directory | Speaks | Read by |
|---|---|---|
| `serial/` | the line protocol between the ATmega2560 and the ESP8266 over Serial3 @ 9600 | C++ only — both ends of that link are firmware |
| `http/` | the request and response BODIES of the device API, and the bearer header every request carries | **C++ and C#** — the firmware renders, the server parses |
| `buttonmap/` | the button-map token grammar and the relay hard cap it is pinned to (`relay_hard_cap_minutes`) | **C++ and C#** — the server validates what an admin saves, the firmware parses what the heartbeat hands it |
| `gate/` | the door gate's three bodies: the heartbeat's `kind` hint and its gate-shaped answer, the `/api/v1/device/gate` scan decision, and the offline `gate_open` event | **C++ and C#** — the gate firmware renders, the server parses |
| `membercode/` | the single rotating member code (D1): SHA-256/HMAC/HKDF/TOTP vectors, the member-secret → K_day → token chain, token parsing, offline verification, the roster's REF lists, the heartbeat's code sync, the court box's and the door's bodies, and D10 pay-for (`payfor.json`, server-only since bridge 3.0.0) | **C++, C# and TypeScript** — both firmwares, the server and the phone; `manifest.json` says which file each reads. | `ota/` | signed OTA for the two ESP chips: the canonical release manifest, the RSA-2048 PKCS#1 v1.5 SHA-256 signature over it, the version gate, the heartbeat's `ota` offer and one small image to stream and hash | **C++ and C#** — the shared `devota` library (and through it the bridge and the gate) verifies; the server verifies an upload against the same key and renders the offer. Generated by `ota/gen_cases.py` with TEST keys only |
| `provision/` | how a board reaches the club: the base-URL grammar, the heartbeat's `net` and `key_next` objects, and the WiFi link supervisor | **C++ and C#** — the shared `devnet` library adopts; the server validates what an admin saves with the same rules. Generated by `provision/gen_cases.py` |
| `display/` | the court box's glass: landing composition for the compact (16x2) and expanded (20x4) layouts, the marquee window, and the CRC a v3 screen commit carries | **C++ and TypeScript** — the Mega composes and checks, the bridge computes the CRC, the console's landing preview renders. Generated by `display/gen_cases.py` |
| `compat/` | forward compatibility for the frozen firmware: every device body's **budget** (the buffer a board reads into, the most the server may send), and what a v3 court box and a v3 door gate **adopt** from bodies a later server might send — extra element fields, unknown keys carrying known names, wrong number kinds, every 2xx, cut and HTML bodies, and the lifeline (`ota`, `key_next`, `net`) surviving a body whose rest has drifted | **C++ and C#** — both firmwares run every case through their own adoption and classification code; the server asserts its widest real bodies against `budgets`. Generated by `compat/gen_cases.py`, the reference implementation of [`device-api.md`](../../../docs/specs/device-api.md) §11 |

`http/` is the one that matters most. A body the firmware renders one field
differently from the way the server reads it is a 400 with no diagnostic, on a
board in an electrical cupboard, and costs a trip to the club to discover.

**`gate/` is a separate family rather than more cases in `http/`, deliberately.**
The court box's C++ suite executes every case in the family it reads and asserts
the count, so a gate vector added to `http/` would make that suite red on a board
that has no gate code in it at all — and the gate's own suite would be counting
the court box's vectors. Separate families keep each side's `executed == declared`
assertion about its own device. The two share the roster element grammar on
purpose (`TOKEN|relay|opens_in|closes_in`, with the relay always `0` on a gate)
so `devlink::parseRosterElement` and `roster::Roster` are reused unchanged, and
that reuse is what makes the shared grammar worth pinning twice.

**`gate/`, `ota/`, `provision/`, `display/` and `compat/` are generated** by the `gen_cases.py` beside each, and so is `membercode/` by `src/iot/tools/membercode_vectors.py`. `gate/cases.json` and `gate/manifest.json` are **generated**, by
`gate/gen_cases.py` beside them: the bodies are written there as shapes and the
hex falls out, so a renamed field is one edit rather than a transcription
exercise. Edit the generator and re-run it; a hand-edited `body_hex` is a hand-
edited byte string, which is exactly the class of mistake this corpus exists to
catch.

It used to hold the canonical signing string and the HMAC of every request as
well. Firmware 2.0.0 replaced request signing with one static per-tenant key in
an `Authorization: Bearer` header — one club, one box — so what is left to agree
on is the body shape and that header. The `discovery/` family went with it: there
is no UDP beacon, no OFFER and no claim commitment any more, because the API base
URL is compiled into the image.

**The three v3 families are generated rather than hand-written because each one IS a reference
implementation**: `ota/gen_cases.py` signs and verifies with the standard library alone (and the
signatures were cross-checked against an independent RSA implementation when the family was
created), `display/gen_cases.py` composes the landing screen, and `provision/gen_cases.py` decides
adoption. A consumer is checked against their output, never against itself. `serial/` and `http/`
stay hand-maintained JSON, with checksums and hex produced by an independent Python pass.

## The rules a frozen reader lives by

The Mega 3.0.0 image is the last that chip gets, and each ESP image is only updatable while its
heartbeat parser, key ring and OTA path keep working. So every family obeys four rules for as long
as any v3 board is in the field ([`device-api.md`](../../../docs/specs/device-api.md) §11):

1. **Additive only.** A field may be added; none is renamed, retyped, moved or removed. A key never
   changes meaning.
2. **Elements grow only at the end.** A `|`-separated element (roster, `courts`, `relays`,
   `code_days`, `code_keys`) may gain fields after its last one, never in place of one; new
   per-element data otherwise goes in a new parallel array.
3. **Known keys live in one place.** `button_map` only inside `config`; the gate's settings only as
   scalars inside `gate`; no other object may carry a key name a board reads.
4. **Inside the budget.** Every body stays inside its `compat/` `budgets` row, and for a v3 board
   that is at most 80% of the buffer it is read into.

`compat/` pins what a board does when a server breaks one of these anyway; the C# suite pins that
the server does not; and `make device-replay-check` runs the server's real replies through both
firmwares' real parsers, because a corpus can only hold the bytes somebody wrote down.

## Anti-drift: executed counts, not checksums

Each `manifest.json` declares `case_count` per file. Both sides assert that the
number of cases they **executed** equals the number declared, and that none was
skipped as an unrecognised kind.

A checksum over the corpus was considered and rejected: it detects that a file
changed, but not that a side quietly ignored the cases it did not understand.
A side that skips what it cannot parse passes a checksum test and fails in the
field. Counting what actually ran is the assertion with teeth.

## Adding a case

1. Add it to the relevant `*.json`.
2. Increment `case_count` in that directory's `manifest.json`.
3. Run both suites. Both must go red before either implementation is changed —
   if a new case passes immediately on both sides, it was not testing anything.
