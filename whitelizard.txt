# Every function listed here already exceeded the gate (CCN 15 / length 200 /
# 6 params) when the gate was introduced. Listing them freezes the debt: they
# cannot get worse without being noticed, and NEW code is held to the real
# threshold from day one.
#
# The right way to remove a line from this file is to simplify the function.
# Adding a line requires a reviewer to agree the complexity is essential.
#
# A note on the Minimal API entries: lizard scores `MapXxxEndpoints` as one
# function, but it is really N independent route handlers, each individually
# simple. Those are measurement artifacts rather than genuine complexity, and
# they resolve naturally as endpoints are split out during the device work.
#
# THE NAMES HERE ARE LIZARD'S, NOT C#'s, and the two disagree. lizard's C#
# parser scopes a function under the most recently DECLARED type, not the type
# that encloses it — so `TopUpEndpoints.MapTopUpEndpoints` is reported as
# `FailureCodes::MapTopUpEndpoints` when the nested `FailureCodes` class is
# declared above it, and as `TopUpEndpoints::MapTopUpEndpoints` when it is
# declared below. An entry written from the source rather than from lizard's
# own output matches nothing and the gate stays red while looking whitelisted.
# Copy the name out of `make complexity`'s warning line; never type it from
# the C#.
#
# WHICH IS WHY THAT ONE FUNCTION IS LISTED UNDER BOTH NAMES. Two rounds fixed
# the same red gate in opposite directions — one moved `FailureCodes` below the
# map method so the reported name became `TopUpEndpoints::`, the other left the
# class where it was and renamed the entry to `FailureCodes::` — and the merge
# took the first branch's source with the second branch's entry, so neither
# matched and the gate went red on a file nobody had edited. An entry that
# depends on where a nested class is declared is a trap whichever way it is
# pointed; naming both costs nothing (no other function in the tree is called
# `MapTopUpEndpoints`) and survives the class being moved again.
