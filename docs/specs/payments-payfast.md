# Payments — PayFast

**Supersedes [`payments-peachpayments.md`](./payments-peachpayments.md).** The provider
changed by founder decision on 2026-08-22; nothing was ever built against PeachPayments
beyond an interface implementation, which is why the switch cost a spec rather than a
migration.

## The shape

PayFast hosted checkout, per-tenant merchant credentials. The member never types a card
number into anything this project serves, which is what keeps PCI scope to a redirect.

```
member                  mainframe                    PayFast
  │                         │                           │
  │  POST /credit/topup     │                           │
  ├────────────────────────►│                           │
  │                         │ writes PendingTopup       │
  │  form fields + signature│                           │
  │◄────────────────────────┤                           │
  │  auto-POST the form                                 │
  ├────────────────────────────────────────────────────►│
  │                                          member pays│
  │◄─── redirect to return_url ─────────────────────────┤
  │                         │                           │
  │                         │◄──── ITN (server to server)
  │                         │  verify, then post credits │
```

**The redirect is not the notification.** A member can close the tab, lose signal, or come
back to the return URL before the ITN lands. The ITN is what moves money; the return URL only
decides which screen they see.

## The signature

MD5 over a parameter string, in **the order the fields are sent**, URL-encoded the way PHP's
`urlencode` does it — which .NET does not:

| | PHP `urlencode` | .NET `Uri.EscapeDataString` |
|---|---|---|
| space | `+` | `%20` |
| `~` | `%7E` | `~` |
| hex case | **upper** | upper |

`PayFastSignature.UrlEncode` implements the PHP behaviour deliberately, and every one of
those three differences is a signature that silently never matches.

Two more rules that are easy to get wrong and produce the same silent failure:

- **Field order is the order posted**, not alphabetical. This is why `CallbackPayload.Fields`
  is an `IReadOnlyList<KeyValuePair<..>>` and not a dictionary — a dictionary destroys the
  ordering the signature is computed over, and the type was changed for exactly this reason.
- **The passphrase is appended as `&passphrase=<urlencoded>`** when the merchant has one, and
  omitted entirely when they do not. An empty-string passphrase is not the same as no
  passphrase.

The algorithm is pinned by [`src/contracts/payfast/`](../../src/contracts/payfast/) — 15
encode cases, 7 payment-request signatures and 4 ITN signatures, generated by an independent
implementation from the published documentation. **That corpus is the authority, not this
document.**

## Receiving an ITN

In order, and each step exists because skipping it has a specific cost:

1. **Verify the signature.** Everything except `signature`, in the order posted, against the
   tenant's passphrase.
2. **Check the source address** against `PayFastProvider.KnownSourceHosts`. Advisory and
   configurable, never primary — a reverse proxy that rewrites the source would otherwise
   reject every genuine notification. It exists because a merchant with no passphrase has
   nothing else.
3. **Check the amount** against the `PendingTopup` row. A signature says the message is
   authentic; it does not say the amount is the one that was asked for.
4. **`payment_status == "COMPLETE"` is the only success.** A valid signature on a `FAILED`
   notification is a valid message saying no money moved. Treating them as the same credits a
   member for a payment that failed.
5. **Post the credits idempotently.** PayFast **retries ITNs by design**, so a duplicate is
   normal traffic rather than an attack. The filtered unique index on
   `LedgerEntry.ExternalReference` is the only database-level guarantee, and it is what makes
   a retry safe rather than a double credit.

There is no status polling. `GetStatusAsync` returns an explicit "not supported" rather than
throwing, so a caller that reaches it gets a decision instead of a 500. PayFast's query API
needs a separate signed request and the ITN already retries until acknowledged.

## Credits, not rand

The member pays rand; the ledger records **credits**. Conversion happens at the tenant's
class-specific rate — `credits_per_zar_regular` (1.6 by default) or `credits_per_zar_league`
(2.4) — and the rand figure is kept on the `PendingTopup` row for reconciliation only.

A ledger field whose name says rand while the column holds credits is a money-correctness
bug, and `CLAUDE.md` forbids adding a second one. See `AmountCredits`, which is
credit-denominated despite a legacy name.

## Configuration

Per tenant, never global:

| Setting | Notes |
|---|---|
| Merchant ID | from the PayFast dashboard |
| Merchant key | from the PayFast dashboard |
| Passphrase | optional at PayFast, **required here** — without one the signature protects nothing |
| Environment | `sandbox` or `live`, selecting the process URL |

**None of these belong in the repository.** They are tenant payment settings.

## Testing it

The corpus proves the algorithm. The [mountebank imposter](../../test/virtualization/README.md)
proves the handling: a decline, a gateway timeout, a replayed ITN, a tampered signature —
cases you cannot ask a sandbox for on demand.

Neither proves the integration works against PayFast. **The first live transaction is a real
milestone** and is item 3 on the [go-live checklist](../go-live-checklist.md).
