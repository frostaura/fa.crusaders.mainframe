# Crusaders Mainframe — Court-Light System: Adversarial E2E Review (Final Synthesis)

## 1. Verdict

The claim "the end-to-end system is flawless given the fixed wiring" is false, and not marginally so: **the system's headline flow — book online, scan at the box, lights on — does not exist end to end in the shipped code, and cannot succeed by any path.** Independent finders and adversarial verifiers, working first-hand against the repo, confirmed seven critical defects, none of them wiring problems: the box can never make its first signed API call (no clock source ever lands on real hardware), the roster the scan path depends on is never populated by anything on either side, no device-reachable activation endpoint exists, the one-box-four-courts hardware is unrepresentable in the shared per-court device model, walk-up purchases charge a different court than the one that lights, and the backend never converts the box's activation evidence into attendance — so the moment the roster gap is fixed, every attended booking gets swept as a no-show, refunded, and penalised. Every one of these fails on real hardware while the host test suites stay green, because the tests inject exactly the data (server time, roster entries, `!BTN`/`!AUTH` frames) that no production path supplies. The fixed wiring is not the problem anywhere; the firmware and backend have simply not finished adapting to it, and the go-live checklist's claim that "the online path is what runs today" is falsified by the code. This system must not go live for booked members in its current state.

## 2. Confirmed findings, ranked by severity

All verdicts below are CONFIRMED by independent adversarial verification. No fix below touches the wiring.

### CRITICAL

**C1. The box can never make its first signed API call — clock seed deadlock.**
`src/backend/.../Endpoints/DeviceEndpoints.cs:166` (provision response) vs `src/iot/src/court_bridge/main.cpp:850-885`, `src/iot/lib/devapi/src/DeviceClient.cpp:28-34, 87-95`.
The firmware seeds its clock from `server_unix` in the provision response — which the backend never sends. `sign()` refuses every request without a clock; the 401 drift-recovery path reads `server_unix` from a body the auth handler never writes; no NTP, no RTC, no persisted offset. Verifiers additionally found the discovery OFFER carries the API clock (`DiscoveryListener.cs:260`, `Offer.h:74`) and `handleOffer` discards it.
*Club-facing failure:* a freshly claimed board shows CONNECTED / SCAN TO START and is permanently mute — no heartbeat, no events, every walk-up says NO CONNECTION. Any power cut deadlocks an already-provisioned board identically.
*Fix:* add `server_unix` to the provision response and a minimal JSON body on Device-scheme 401s; and/or adopt the signature-verified offer time in `handleOffer` (this also fixes post-reboot recovery, which the backend-only fix does not). Pin with contract vectors.

**C2. Nothing on either side ever fills the roster and the firmware has no online scan path — every booked member's scan is refused, forever.**
`src/iot/src/court_bridge/main.cpp:1122-1130, 525-538`; `src/iot/lib/roster/include/roster/Roster.h:12-14, 213-218, 239-244`; `src/backend/.../DeviceEndpoints.cs:86-112`. (Two independent finders converged on this; both confirmed.)
`Roster.h` promises "the API pushes the roster on the heartbeat"; the backend has zero occurrences of "roster" and the heartbeat config carries only slice/grace/button_map. `beginReplace/add/commitReplace` are called only in host tests. `decide()` returns `Stale` before matching when never loaded; `handleScan` makes no API call.
*Club-facing failure:* every paid member scanning at a healthy, online box sees "NO CONNECTION / SEE THE DESK" and a dark court — every scan, every court, indefinitely. Charge-at-booking means they were already debited; no activation event fires, so the no-show sweep later penalises them (see C6). Go-live item 11 cannot pass, and item 10's framing ("the online path is what runs today") is false against the code and corrupts the gate that should force the fix.
*Fix:* add a per-court near-future bookings array to the heartbeat response and parse it into `beginReplace/add/commitReplace` in the Accepted branch — or add an interim online scan-verification call on the scan path. Correct go-live item 10.

**C3. No path in the whole system lights a court for a pre-booked member — and the walk-up fallback is blocked by their own booking.**
`src/backend/.../DeviceEventEndpoints.cs:42-52`; `src/iot/src/court_bridge/main.cpp:525-537`; `src/backend/.../Services/BookingService.cs:162-166`; `Program.cs:223-224`.
The device surface is only /provision, /heartbeat, /events, /walkup. The activation endpoints that stamp `CheckedInAt` require an admin JWT the box cannot present — and even those actuate nothing (`NullRelayClient` is the sole `IRelayClient`; `TurnOnAsync` has no production caller; the HTTP-client-only ESP cannot receive the webhook mirror). The member's fallback — buying time at the pad — hits the `inProgress` predicate, where their own paid booking returns SlotTaken → 409 → "COURT NOT FREE". Scanning early instead sells them the gap before their own slot: paid twice, court still dark at start.
*Club-facing failure:* member pays online, stands at a dark court, is refused on both the scan and button paths, then is flagged a no-show and charged the penalty. Only unbooked walk-ups work at all (subject to C4/C5).
*Fix:* add a device-authenticated activation endpoint (`POST /api/v1/device/activate {method, token}`) resolving the token to an activatable booking on the device's courts via `CourtActivationService`, returning granted seconds for the `!ON` — the mirror of the walk-up flow. Firmware calls it when the roster refuses.

**C4. One physical box serves four courts, but the shared device model is per-court — the scan path can structurally light at most one court, and the firmware never even adopts its court assignment.**
`src/iot/src/court_bridge/main.cpp:239, 536`; `Roster.h:256-262`; `src/backend/.../AdminDeviceEndpoints.cs:110`; schematic (relays A–D → pins 2–5) and IMG_1159 (one scanner, four relays).
`Device.CourtNumber` is a single int; the backend requires exactly one court per CourtBox; `gCourtNumber` is declared 0 and never assigned (the heartbeat sends it, `pumpHeartbeat` never parses it); `onScan` can only light the court passed in, never the matched entry's court. Even after C2 is fixed, members booked on B/C/D are refused as WrongCourt at the club's only scanner — with the no-show penalty consequence on top. Today the shipped reality is zero of four courts (everything is Stale).
*Fix:* let a CourtBox own a set of courts in the backend; in firmware, resolve the court from the matched roster entry (`entry.court` is already carried) and light that relay; parse `court_number`/court-set from the heartbeat.

**C5. Walk-up books and charges the device's single configured court while the box lights whichever court the member selected.**
`src/backend/.../DeviceEventEndpoints.cs:208-213` vs `src/iot/src/court_bridge/main.cpp:754-796`; `ButtonMap.cs:84-94` (default map is courts A–D).
The walk-up request carries no court field at all (`{minutes, method, token}`); the backend books, availability-checks and charges `device.CourtNumber`; the firmware lights `intent.court` from the pressed button. The backend's own button-map feature is unrepresentable by its own walk-up contract.
*Club-facing failure:* box registered as court 1; member presses COURT C + 60 min → court 1's slot is consumed and charged, court C's relay lights. Ledger and physical lights diverge on every walk-up for three of four courts; conversely, court 1 busy + C free yields 409 "COURT NOT FREE" for an empty court.
*Fix:* carry the selected court in the walk-up request, validated against the device's court set (per C4); book, price, truncate and echo against that court.

**C6. Box activation events are never turned into attendance — the no-show sweep refunds and penalises members who actually played.**
`src/backend/.../DeviceEventEndpoints.cs:63-167`; `NoShowWorker.cs:239, 100-116`; `CourtActivationService.cs:198`.
The firmware's whole offline money model rests on the queued Activation event stopping the refund (`Session.h:16-22`). The /events handler writes only a `DeviceEventReceipt` and an `AuditLog` — it never resolves the booking or sets `CheckedInAt`, and nothing else consumes the receipts. Worse, server acknowledgment makes the box release the queued event, destroying the evidence. Latent today only because C2 prevents activations from firing; **shipping the roster fix without this one converts every attended box check-in into a full refund plus penalty against the club.**
*Fix:* in /events, for `kind=="activation"` resolve the booking from (court, token, window) and run it through the single `CourtActivationService` path, idempotent on (device_id, seq). Must land in the same release as the C2 fix.

### HIGH

**H1. The bridge never sends `!AUTH`, so the Mega discards every button press — walk-up purchase and early release are dead at the panel.**
`src/iot/src/court_bridge/main.cpp:525-538`; `lib/courtlogic/src/CourtBox.cpp:126-134, 219-221`; `docs/specs/device-serial-protocol.md:51, 95`.
The auth window is armed only by a received `!AUTH` frame; `proto::Frame::auth` is constructed nowhere in the bridge (its complete outbound vocabulary is lcd/on/off/ping). The old sketch armed it implicitly on the LCD prompt; v2 dropped that without ever sending the explicit replacement. `CourtBox.h:129` even documents this exact symptom. Tests inject `!BTN` directly and stay green.
*Club-facing failure:* no walk-up can be sold at the pad; a member finishing early cannot release the court, so every session records full booked length.
*Fix:* bridge sends `Frame::auth(30)` (config-driven TTL) after a scan is remembered, `!AUTH,0` when scan memory lapses.

**H2. No token format can both transit the scanner pipeline (≤24 bytes) and be verified by the backend (a JWT) — device identification can never succeed.**
`lib/protocol/include/protocol/Protocol.h:58`; `lib/courtlogic/include/courtlogic/ScanAssembler.h:46`; `Roster.h:52`; `main.cpp:765`; `src/backend/.../IdentificationResolver.cs:52-113`; `QrEndpoints.cs:34-61`.
`kMaxArgLen=24` and the assembler poisons (never truncates) longer lines; the only QR the system mints is a multi-hundred-byte HS256 JWT. The real QR is dropped as TooLong at the Mega; anything that fits fails JWT validation → 400 → "SEE THE DESK". Separately `roster::kMaxTokenLen=40` invites tokens 16 bytes longer than the pipeline can ever deliver, with no compile-time tie.
*Fix:* define the at-box identifier (go-live item 10's open decision) at ≤24 bytes with its own verification path on the device surface; statically assert `roster::kMaxTokenLen <= proto::kMaxArgLen`.

**H3. Walk-up purchase is not idempotent — a lost HTTP response leaves the member charged, the court dark, and every retry answered 409.**
`src/backend/.../DeviceEventEndpoints.cs:183-260`; `main.cpp:768-779`; `BookingService.cs:162-166`.
Booking, debit and `CheckedInAt` all commit before the 200 is written; the firmware sends `!ON` only on a received 200 (4 s timeout, WiFi transport); a retry hits the member's own fresh booking → SlotTaken. `CheckedInAt` being stamped also suppresses the no-show refund. The repo documents this exact idempotency requirement twice (`IRelayClient.cs`, the /events (device_id, seq) design) and skips it on the only money-moving device call.
*Fix:* client-generated purchase nonce; on replay return the original grant so the box can `!ON`. Or: a repeat scan by the same user of their own live walk-up returns remaining minutes instead of SlotTaken.

**H4. Biometric candidate selection is unordered — the documented two-bookings wrong-row bug, fixed at two of three sites, is still live on the biometric path.**
`src/backend/.../Biometric/BiometricService.cs:79-95`.
`CourtActivationService` fixed `CandidatesAsync`/`FindForUserAsync` with `OrderBy(StartsAt)` for exactly this bug; `MatchAtCourtAsync` builds a third, unordered query and takes `FirstOrDefault`. The pinned regression test's comment falsely claims the biometric path reads the ordered list, so the suite is green while the bug is live — and `NullBiometricDevice` produces real matches today.
*Club-facing failure:* member with back-to-back 17:00/17:15 slices matches at 16:58; if Postgres returns 17:15 first, the wrong row activates, the 17:00 booking sweeps as a no-show, and the member is penalised while standing on the court.
*Fix:* route through `CandidatesAsync` (join templates after), or same OrderBy + earliest-for-user; pin with a two-bookings test through `MatchAtCourtAsync`.

**H5. A settled no-show holds the slot until EndsAt — the agreed "no-show releases the court" rule is violated by predicates and the GiST constraint alike.**
`Migrations/20260823123826_AddBookingOverlapExclusion.cs:56`; `BookingService.cs:70-74, 162-176`; decision record in `memory/decisions.md`.
The exclusion constraint and all overlap predicates exempt only Cancelled; nothing truncates a swept NoShow row, and verifiers found admins cannot even cancel one (`CancelAsync` requires Booked).
*Club-facing failure:* member no-shows 18:00–19:00; by ~18:06 the club has refunded ~70% and cannot resell the hour — online bookings get SlotTaken and the pad answers "COURT NOT FREE" for a visibly empty court, with no admin recovery path.
*Fix:* truncate `EndsAt = now` in the same save as the settlement, or exempt settled NoShow from the constraint and predicates; align the migration comment with the recorded decision.

### MEDIUM

**M1. Walk-up can sell up to 240 minutes while the relay hard cap silently clamps actuation to 90 — member pays for darkness with no refund and no re-light path.**
`DeviceEventEndpoints.cs:206` (hardcoded 240, also violating the tenant-settings invariant); `lib/protocol/src/Protocol.cpp:158-163`; `RelayGuard.h:62`; `ButtonMap.cs` ("a club that wants three hours can set 180").

**M2. The ESP never adopts the court number the backend assigns it — `gCourtNumber` stays 0 for the life of the box.**
`main.cpp:239, 536`; backend sends it at `DeviceEndpoints.cs:92`; `pumpHeartbeat` never parses it.
Confirmed dead-field defect, downgraded because it is currently masked by C2 (every scan is Stale before the court is compared) and is subsumed by C4's model mismatch — on a one-scanner/four-court box, adopting any single court number still misattributes three courts. Fix it as part of C4 (court from the matched roster entry), not in isolation.

# Addendum — Round 2 Findings (17 verified)

Round 2 verified the remaining 17 findings against the repo, the canonical wiring sheet, the build photos, and the old proven-working sketches. **16 are confirmed, 1 is refuted.** All fixes below respect the fixed-wiring constraint: every one is a firmware, backend, config, or documentation change — none touches the board.

## Confirmed findings

### High

**A2-1. The repo declares the first ESP8266 flash DIP position undocumented — the canonical sheet documents it, and the README silently dropped that row.**
The canonical wiring sheet carries a dedicated row for the ESP8266 bridge: Upload DIP `1 OFF, 2 OFF, 3 OFF, 4 OFF, 5 ON, 6 ON, 7 ON, 8 OFF`, differing from run/monitor only in DIP 7 — the GPIO0/flash-mode line on WeMos Mega+WiFi boards. `src/iot/README.md` (lines 64–79) reproduces four sheet rows but omits exactly this one, then claims the sheet "documents positions for Serial3↔ESP and USB↔Mega, but not for USB↔ESP8266 with GPIO0 pulled low" and prescribes an external USB-TTL adapter soldered or clipped to the ESP module's pads with GPIO0 grounded. The false claim is repeated verbatim in `docs/go-live-checklist.md` item 5 (lines 88–101), `memory/watch.md` item 4 (lines 27–30), and `memory/questions.md` line 15; a repo-wide grep for "7 ON" returns nothing, so no document corrects it. **Club-facing failure:** a technician follows the repo's only DIP documentation, concludes no ESP upload position exists, stalls the go-live schedule hunting for a USB-TTL adapter, and then clips or solders onto the pads of the fixed, working build — physical intervention on hardware whose wiring must not be touched, all to avoid flipping one documented switch. **Fix (docs only):** add the sheet's ESP Upload row to the README DIP table and delete the "not documented / may need USB-TTL" caveat from all four locations, replacing it with the documented DIP 5+6+7 ON position as a checklist verification tick.

**A2-2. Three mutually exclusive stories about the OTA signing key — and "If skipped: OTA works" is falsified by the repo's own contents.**
`docs/go-live-checklist.md` item 6 (lines 105–129) claims the committed key is "a working default" such that "anyone with the repository can sign firmware" and "If skipped: OTA works"; `memory/watch.md` item 5 repeats that "the committed key's private half is a repo default"; `MEMORY.md` line 7 says the key "does not exist yet"; and `OtaPublicKey.h` says the private key "is NOT in this repository… it lives with whoever cuts releases." At most one of these can be true, and verification shows none of the consoling ones are: only the public half is committed, a repo-wide search finds no private key anywhere (repo, CI secrets, adjacent locations), `generate_ota_keys.sh` refuses to regenerate the same pair, and no document records where the private half went after commit 9f82afc generated it. Because `main.cpp:953–1013` compiles the public key in and enforces `Update.installSignature`, every board flashed with the current header rejects every image nobody can sign — OTA is dead on arrival, not "working but insecure." **Club-facing failure:** the club skips item 6 on the strength of "If skipped: OTA works," flashes the fleet over USB, and the architectural premise of the thin Mega — the ESP updates over the air — silently collapses to USB-only until every board is opened up and re-flashed with a rotated key. **Fix (docs/memory only):** establish whether the private half of the committed key exists anywhere and record where; if unlocatable, rewrite item 6 so key generation is a hard first-flash prerequisite ("If skipped: OTA is impossible for boards flashed with this key"), fix watch item 5, and correct the stale claim in the owning memory topic — the index hook is the topic's `description:` field and `MEMORY.md` is regenerated from it, never hand-edited.

### Medium

**A2-3. The "release job" the OTA procedure depends on does not exist.**
Checklist item 6 instructs "Set OTA_PRIVATE_KEY in the release job… The build then produces firmware.signed.bin automatically," and `src/iot/tools/pio_sign_post.py` says "only the release pipeline (which sets $OTA_PRIVATE_KEY from a secret) cuts an image OTA will accept" — but `.github/workflows/ci.yml` (the only workflow) contains no step that sets `OTA_PRIVATE_KEY`, signs firmware, uploads a firmware artifact, or hosts a `.bin`. The existing release chain builds Docker images for backend/frontend only; the firmware steps are a signer self-test and a plain compile. The checklist's own six-secret list omits `OTA_PRIVATE_KEY`, and no document anywhere describes who builds, signs, and serves the URL that `OtaCatalogue.cs` reads from `Ota:Stable:Url`. **Club-facing failure:** an operator reaches item 6 with no job to put the secret in and no hosted image to point config at; OTA stays theoretical until someone improvises an unversioned by-hand build-sign-host path — the exact class of undocumented manual step the checklist exists to eliminate. **Fix (CI/docs):** either add a signing-and-publishing job to `ci.yml` gated on the secret and add the secret to the checklist's list, or rewrite item 6 as an honest end-to-end manual procedure including where the signed `.bin` is served from.

**A2-4. webhooks.md justifies the SSRF carve-out with a "fixed RFC1918 address" the discovery spec forbids, describing an actuation path the shipped firmware cannot receive.**
`docs/specs/webhooks.md` (lines 146–152) says the LAN carve-out exists "because a court box lives at a fixed RFC1918 address" and offers `"192.168.68.150/32"` as the example — which is Carl's retired hardcoded static, and which `docs/specs/device-discovery.md` line 19 directly contradicts ("DHCP everywhere and no static addresses on either side," with "DHCP moves the box mid-session" as a modeled failure). The bridge firmware has no inbound HTTP listener of any kind — it only POSTs out — so the box can never be a webhook destination; and `CLAUDE.md`'s carve-out sentence points at an architecture `lights-controller.md` itself marks Superseded. Neither the go-live checklist nor `docker-compose.onprem.yml` mentions `PrivateNetworkAllowList`. **Club-facing failure:** an admin registers box-addressed lights webhooks pinned to a DHCP lease; every delivery fails, hits the 6-failure auto-disable, and emails the owner — noise misread as a lights outage — while blocked destinations are abandoned without retry, so a lease change silently kills any legitimate LAN consumer, and the operator believes a remote off-switch exists that does not. **Fix (docs only):** rewrite the carve-out rationale for the shipped pull-only device design, delete the fixed-address claim and the retired-address example, correct the CLAUDE.md sentence, and add allow-list/DHCP-reservation guidance to the ops docs for any real LAN webhook consumer.

**A2-5. memory/state.md presents multiple falsified claims as current.**
`memory/state.md` line 196 lists "Not started: PayFast… Phase 5 court firmware… Phase 8 OTA" — contradicted by the same file's lines 106 and 141, by `MEMORY.md` ("Phases A–J code-complete"), and by real code (`Payments/PayFast/`, three compiling firmware targets, signed OTA). Line 186's "Device has no MAC column" is falsified by migration `20260822235151_AddDeviceMacAddress`, `Domain/Device.cs:86`, and its tests. Lines 183–185's "the claim flow stops at returning the key" is falsified by `POST /api/v1/device/provision` and the discovery spec's board-fetch section. **Club-facing failure:** the next agent reads the file's closing "still red or unbuilt" section — the natural place to look — and re-plans or re-implements built systems; `memory/gotchas.md` records this exact pessimistic-stale class "nearly caused the work to be done twice." **Fix (memory only):** strike or prune lines 180–196 so the closing section agrees with the file's own opening and with MEMORY.md, restamping `last_verified` only for what was inspected.

**A2-6. A dropped `!EVT,AUTOOFF/OFF` is unrecoverable — the Mega's comment claims `!STATE` lets the bridge find out, but the bridge explicitly ignores `!STATE`.**
`CourtBox.cpp:153–155` asserts "publishing the new state is how the bridge finds out… whether or not the events got through," but the bridge's `handleUplink` default branch (`main.cpp:618–623`) discards `!STATE` without parsing ("read for diagnostics only"). `sendFrame` drops any frame when the 64-byte AVR TX ring lacks room (draining at ~1 byte/ms at 9600 baud; four simultaneous court expiries guarantee a drop), nothing retries a dropped EVT, and the bridge's session has no timer of its own — `onRelease` is reachable only from the event handler. **Club-facing failure:** one dropped `AUTOOFF` and the bridge's held-state never clears, no Release event reaches the API, and the club's record shows the court used for its full booked length regardless of the actual auto-off — the actual-usage number the Mega's timer exists to produce is silently wrong, with no trace on either side. **Fix (firmware only):** make the bridge reconcile held/session state from `!STATE` transitions (mask bit cleared → treat as release), or have the Mega retry dropped court events the way it retries the OVERRUN notice; correct the CourtBox comment either way.

**A2-7. A fully provisioned, in-service board repaints the CLAIM CODE over its idle screen on any Mega reset or WiFi reconnect.**
`showClaimPrompt()` (`court_bridge/main.cpp:321–326`) has no provisioned guard and is called from `noteMegaPong` on any detected Mega restart (lines 499–503) and from `pumpWifiLink` on every WiFi link-up (lines 896–908) — including the first connect of a normal power-on. `gClaimCode` is regenerated every boot, so the code shown on a claimed board is stale and meaningless, and no periodic idle repaint exists, so the prompt persists until the next scan or button press. The `Reprovision` path sets `gProvisioned=false` before calling it, confirming the prompt is meant as an unclaimed-state screen. **Club-facing failure:** a brown-out, DIP toggle, or WiFi blip on a live court paints "CLAIM CODE \<hex\>" over the working idle screen; the court still works, but staff and members read it as an unclaimed or broken box and generate support calls. **Fix (firmware only):** guard `showClaimPrompt()` or its two call sites on `!gProvisioned`, repainting the idle screen instead on a provisioned board.

**A2-8. Go-live checklist section 8 misdescribes the fixed power topology — the ESP under WiFi load is not on the LM2596 5V rail it tells the electrician to measure.**
`docs/go-live-checklist.md:146–157` claims "Two ESP nodes share an LM2596 rail with relay coils, the LCD backlight and the scanner" and prescribes measuring the 5V rail with WiFi transmitting. The fixed wiring (schematic + photos IMG_1160/IMG_1162, two independently fused LM2596 modules labeled 5V and 9V) puts the court box's only ESP node — the onboard ESP8266 — behind the Mega's regulators fed from the 9V buck via VIN/barrel jack; the 5V buck feeds only LCD, scanner, and relay VCC. The "two ESP nodes" can only be the founder-parked gate ESP32s in a separate box on their own supply, so the sentence is wrong under every reading. **Club-facing failure:** the prescribed brown-out test measures the wrong rail — it can pass while the actual ESP brown-out risk on the 9V/VIN path goes unexamined — and later random resets get condemned by the OTA boot guard as a failed firmware, precisely the failure the section warns about; an electrician might also "split" a 5V rail the ESP was never on. **Fix (docs only):** rewrite section 8 to the fixed two-rail topology — measure the 5V rail (relays + LCD + scanner) and the 9V/VIN path under WiFi transmit separately — and drop or relocate the "two ESP nodes" framing to the parked gate box.

**A2-9. The biometric court endpoint discards the ActivationResult — refusals are reported to the kiosk as a plain successful match.**
`BiometricService.cs:112–124` awaits `ActivateAsync(...)` without capturing the return, and `BiometricEndpoints.cs:110–118` returns only `{ matched, user_id, confidence, liveness, latency_ms }`. `CourtActivationService` returns refusals as values (InsufficientBalance, NotChargeable) with only a server-side log, so the discarded result is invisible at the kiosk. PIN and QR both use `CourtActivationResponse.For`, whose stated purpose is that the three touchpoints "cannot drift into describing the same outcome three ways" — the biometric endpoint is exactly that drift. **Club-facing failure:** a volunteer presents "I'll pay" with too few credits; `ChargeOnActivationAsync` refuses the reassignment and leaves the booker as payer, yet the kiosk shows `matched: true` — both players believe the volunteer paid, the booker's account silently keeps the charge, and any dispute lands on the club. Same blind spot for not-chargeable and balance-refused walk-up bookings: matched, no lights, no explanation on the one screen in front of the member. **Fix (backend only):** return `CourtActivationResponse.For(result, userId)` from the biometric endpoint like PIN/QR, carrying the activation outcome alongside confidence/liveness.

**A2-10. ChargeOnActivationAsync checks balances without the payer lock the booking path deems mandatory — the documented double-spend race survives on the activation/reassignment paths.**
`PayerLock.BeginAsync` appears exactly once in the codebase (`BookingService.CommitAsync:254`), where the code's own comment explains it exists because two unlocked balance reads both saw sufficient funds and both debited. `ChargeOnActivationAsync` (lines 572–694) performs the identical read-then-post pattern on both the payer-reassignment branch and the never-charged branch with no lock, and its sole production caller adds none. Balance is an unlocked SUM with no constraint, so `CommitAsync`'s lock cannot serialize a debit that never takes it; the existing concurrency test covers only two writers of the same booking row, not two debits against the same payer from different bookings. **Club-facing failure:** a volunteer with 200 credits says "I'll pay" at one court in the same seconds their own walk-up or a second reassignment commits — both reads see 200, both post, the volunteer lands negative — the exact overspend the payer lock was introduced to make impossible, on the courtside path where double-taps and retries are most common. **Fix (backend only):** wrap both debit branches of `ChargeOnActivationAsync` in `PayerLock.BeginAsync` on the user being charged, mirroring `CommitAsync`.

**A2-11. The 2-hour forward activation window stamps CheckedInAt — forfeiting all refunds — and cues lights up to two hours before a booking starts.**
`CourtActivationService.cs:89` sets `ForwardWindow = 2h`, documented only as back-to-back disambiguation, but all three identification paths (QR, PIN, biometric) admit any Booked row with `StartsAt < now+2h` and pass it to `ActivateAsync` with no proximity gate. Lines 198–199 stamp `CheckedInAt`/`LightsOnCuedAt` unconditionally and line 266 emits `lights_on` with `duration_seconds = EndsAt − now`, spanning the entire idle gap. `SettleCancellation` (BookingService.cs:416–417) returns (0,0) whenever `CheckedInAt` is set, and `CancelAsync`'s AlreadyStarted guard does not fire for a future slot. **Club-facing failure:** a member with an 18:45 booking scans at 17:00 out of curiosity — attendance is recorded 105 minutes early, the mirror declares the court lit until 19:00 across other members' intervening sessions, and if the member then cancels the not-yet-started slot they get nothing back even though the club could resell it. "Attendance means CheckedInAt" is falsifiable two hours early by one accidental scan. **Fix (backend only):** gate the CheckedInAt stamp and lights cue on `now >= StartsAt − grace` while keeping earliest-booking selection for back-to-back disambiguation, or make the forward window a tenant setting per the configurable-number invariant.

**A2-14. Scan feedback the old sketch gave unconditionally was dropped — with the ESP dead, the box shows nothing on a scan.**

## Refuted findings

- **Concurrent overlapping /events uploads can acknowledge unrecorded events** (`DeviceEventEndpoints.cs:143–158`) — **REFUTED.** The load-bearing premise (a retry batch is a superset of the in-flight one) is false for the only production client: the bridge's `drainEvents` sends exactly one event per request from a peek-then-release queue, so any retry is byte-identical to the in-flight request and the optimistic `accepted_through` on a 23505 is always correct — the concurrent request genuinely recorded that seq. Retained as a latent hazard only: the endpoint's `MaxBatch=32` invites a future batching client for which the catch block would be wrong; worth defensive hardening (re-query receipts in the catch), not a reproducible data-loss bug.

## Closing note

Combined with round 1's 14 confirmed findings (7 critical), the picture is now 30 confirmed defects across two rounds, and the addendum sharpens the shape of the risk. The two high-severity findings here are both **documentation actively steering people into harm on the fixed hardware**: the repo's only DIP documentation instructs physical intervention (soldering to ESP pads) that the canonical sheet makes unnecessary, and the OTA checklist's "If skipped: OTA works" consolation would have the club flash a fleet whose over-the-air update path is dead on arrival. Neither requires a line of firmware to fix — but both, unfixed, convert the go-live checklist from a safeguard into the source of the incident.

The medium tier splits into two coherent clusters. First, a **money-integrity cluster** on the courtside activation path — the biometric endpoint swallowing refusals, the missing payer lock, and the 2-hour early check-in forfeiting refunds — which together mean the path members actually use at the club is the one path where wrong charges, double-spends, and silent forfeitures can occur without anyone seeing an error. Second, a **truth-decay cluster** — state.md's falsified "unbuilt" claims, the webhook spec's retired-static-address rationale, the phantom release job, the wrong power-rail test — where the repo's own documents contradict the code, the wiring sheet, or each other, and the operator or next agent acting on the stale layer does the damage.

Round 1 established that the core system has real defects; round 2 establishes that the surrounding operational layer — checklists, memory, specs, and the firmware's failure-mode behavior — cannot yet be trusted to get a technician, an operator, or the next agent safely through go-live. The wiring is fixed and fine. Everything written about it needs to catch up before anyone at the club acts on it.
