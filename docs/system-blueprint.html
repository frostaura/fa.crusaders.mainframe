System · End to end

Topology — from tap to relay coil

Everything runs on one on-prem machine at the club behind a Cloudflare tunnel; the court box is the only other computer. The API never dials the box — every call is box → API, signed. A scan asks POST /api/v1/device/activate first and is decided from the heartbeat-pushed roster only when the API could not be asked; the mains-side safety timer lives one hop further down, on the Mega itself.

Online first; the court still works when the network does not

A scan asks the API — only it knows about a booking made thirty seconds ago or a balance too low to admit — and its answer is final. When the API cannot be asked (no link, no clock, a 5xx, a malformed 200) the box decides from the roster the last heartbeat pushed, and the API hears about it later via the sequence-numbered event queue.

Charge at booking — decided 2026-08-22

Booking posts the BookingCharge debit in the same unit of work as the slot. Supersedes the blueprint's charge-on-lights-on; committee sign-off pending.

Two fail-safes point opposite ways — on purpose

The relay timer fails open (lights off even if everything above dies). The roster cache fails closed (a stale roster refuses entry). Both are correct.

Hardware · Overview

The court box

A WeMos Mega 2560 with its onboard ESP8266, driving four court-light relays, a 20×4 2004A LCD driven as 16×2, an eight-button panel and a QR scanner. The wiring is fixed and cannot change — every pin, serial port, baud rate and DIP position below reflects hardware already built and working. Firmware adapts to the hardware, never the reverse.

Why the brains live on the ESP8266

The ATmega2560 cannot be flashed over WiFi: its ESP8266 sits on Serial3, not the Serial0 bootloader port, and no GPIO reaches the Mega's RESET pin — adding one would be a wiring change. So the split is deliberate:

ATmega2560ESP8266
Rolethin I/O, near-staticall the brains
Ownsbuttons, scanner framing, relay drive, LCD — including the CHECKING... it paints itself on every scan, so a dead ESP is visible on the glass — and the independent auto-off timerprotocol, device auth, heartbeat, the scan decision (lib/bridgelogic: online-first, roster fallback), !AUTH arming, !STATE reconciliation, roster cache, event queue, OTA
Updated byUSB, rarelyover the air

In the system this replaces, the off command was scheduled inside an Excel macro on a Windows PC — close the workbook mid-session and a court burned until somebody noticed. The Mega's timer is independent precisely so that if the ESP hangs, WiFi drops and the backend dies, the lights still go off.

⚠ Relays — open safety question, gates go-live

The relay module is rated 10 A @ 250 VAC. Plausible for one modern LED court bank; inadequate for older metal-halide. Standard practice is relay → contactor coil, contactor carries the lighting load. Not yet confirmed on the installed hardware. If relays switch lighting directly, a qualified electrician is required before anything ships. No software decision changes this.

The display is 20×4 driven as 16×2

The physical panel is a 2004A, but firmware drives it as 16×2 by decision — works on either panel. Geometry is a compile-time constant (LCD_COLS/LCD_ROWS): widening later is a one-line change plus a corpus update.

Hard limits burned into the Mega

RELAY_HARD_CAP_MS = 90 min — no frame can express indefinite-on, and the same 5400 s is now one constant on both sides: proto::kRelayHardCapSeconds (static-asserted in the ESP build too) and the backend's RelayHardCap, pinned by the buttonmap corpus, so the button map, a walk-up and an activation can no longer sell minutes the relay will not deliver. AUTH_TTL_MS = 30 s — button authorisation expires. Both hold regardless of what the ESP, network or backend believe.

Clock — how a box with no RTC gets one on every path

The box signs every request with its own clock and cannot sign without one; review C1 found no production path ever seeded it. Now: the provision response carries server_unix (the first seed a fresh board sees), every heartbeat carries it, and every Device-scheme 401 writes {"server_unix":…} and nothing else — refusal reasons stay unleaked. A provisioned box also adopts the clock in the HMAC-verified, nonce-bound discovery OFFER (an unclaimed box's offer is unsigned and never trusted), which is how a power-cycled board recovers without touching the API. A clockless provisioned box probes: it signs a heartbeat with timestamp 0 and reseeds from the 401 body. Skew tolerance is asymmetric by contract — client 90 s < server 120 s, pinned as the corpus's clock object — and a two-strike ClockCorrected → Reprovision guard in DeviceClient::react stops a 401 loop.

Event queue

A RAM ring of what the box did, drained to the API when reachable. Survives WiFi loss, router reboots, a two-day outage — not a power cut (events outsize the 32-byte hal::IStore slots). The sequence number does persist, in blocks of 64 — that's what API-side deduplication rests on. Only the roster path queues: an activation the API itself granted is one it already recorded. A queued activation is evidence, not a charge — it is what stops the no-show sweep reversing a debit already posted at booking, and since this branch the API actually reads it as attendance (review C6).

The rollover rule

millis() wraps every ~49.7 days and a box in a cupboard is normally up that long. Never compare times directly — use tb::reached(now, deadline) / tb::Deadline. The predecessor firmware got it wrong in both directions on adjacent lines (0-as-sentinel, and now >= expiresAt — false for 49.7 days after the wrap, so the relay was never released). make lint-iot greps for raw deadline comparisons outside lib/timebase.

Over-the-air updates (ESP8266 only)

Signing

RSA-2048 / SHA-256 via the ESP8266 core's Updater, against a public key compiled into the image. Ed25519 was the plan; BearSSL has no Ed25519 and vendoring a curve into a court-lighting controller is the worse trade. The property that mattered survives: the signing key is asymmetric and lives only where releases are built — now concretely CI's iot-sign job, fed by the OTA_PRIVATE_KEY secret (deploy chain). The private key does not exist yet; minting it is a hard prerequisite of the first flash, not a hardening step after it.

No rollback

A 4 MB part with a 1 MB sketch + 2 MB LittleFS has no second OTA slot, and the filesystem holds the device credential. A box that won't boot at all still needs a USB cable.

BootGuard

Ensures a bad build is never installed twice — the fleet-killer, since every box heartbeats the same manifest. Clears on evidence (an API call the server accepted), not on "it booted". Three boots allowed before a build is condemned — brownouts are real when four relay coils energise at once. Condemned versions surface on the Devices screen.

Protocols · Wire format №1

Serial protocol v2 — Mega ↔ ESP8266

9600 8N1 over Serial3, line-terminated, NMEA-style XOR checksum. v2 exists because the legacy protocol had two defects that can't survive being driven by a server: ON had no duration (the off command lived in a VBA macro on a Windows PC) and no integrity (a corrupted a arriving as A turns lights on and leaves them on). v2 is additive — every legacy verb still works in both directions.

LIVE FRAME BUILDER — real XOR checksum, computed as you click

Downlink — bridge → Mega

FrameMeaning
!ON,<court>,<seconds>Close relay for at most that long. Duration is mandatory
!OFF,<court>Open the relay now
!EXT,<court>,<seconds>Extend deadline to now + s. Refused if relay is open
!LCD,<line1>,<line2>Display; truncated to 16 columns
!AUTH,<seconds>Accept button input this long; 0 disarms
!RSTRelays open, buttons disarmed, default screen
!PINGAnswered with !PONG

Seconds are clamped, never rejected (saturating, not wrapping): a clamped light is a wrong-length game; a rejected one is a dark court. AUTH clamps 0–5400; ON/EXT clamp 1–5400 — zero is an OFF wearing an ON's clothes.

Uplink — Mega → bridge

FrameMeaning
!BTN,<key>Debounced press, key ∈ A–D, 1–4
!SCAN,<code>Complete line from the QR scanner
!STATE,<mask>,<remA..D>Relay bitmask + seconds remaining — on change and every 10 s. Read, not just logged: the bridge reconciles its held state from the mask (review A2-6)
!PONG,<ver>,<uptime>Answer to PING
!EVT,<name>,<detail>AUTOOFF · AUTHEXPIRED · BADFRAME · OVERRUN

Bounds: kMaxArgLen 24, kMaxFrameLen 192. Over-long LCD text is truncated (the panel cuts it anyway); an over-long SCAN is refused — a truncated member code doesn't fail, it identifies a different member. That 24-byte argument is the pipeline that ruled a JWT out (review H2): the identifier is now a 12-character access code, and roster::kMaxTokenLen 20 ≤ kMaxArgLen is static-asserted where the two meet.

The two safety rules live on the Mega

1 — Every ON carries a deadline. v2 cannot express indefinite-on; RELAY_HARD_CAP_MS (90 min) caps even a frame that asks for more. A Mega whose bridge is unplugged still opens its relays. 2 — Authorisation expires. !AUTH arms buttons for a bounded window (30 s = AUTH_TTL_MS); the legacy authenticated flag had no expiry, so a button pressed hours after someone else's scan fired a relay on their credit. Review H1 found the bridge never sent !AUTH, so every button press was discarded; it now arms on every remembered scan and sends !AUTH,0 the moment any path — online, roster or walk-up — lights the court (bridgelogic::spendsScan), so the next walk-up never gets thirty seconds of buttons on a stranger's token.

Protocols · Wire format №2

Discovery & claiming — UDP 48653

DHCP everywhere, no static addresses on either side. The constraint that shapes everything: the API runs in a Docker container on a bridge network, and broadcast/multicast frames from the club LAN never cross a bridge — so the discovery listener ships as a host-networking override (docker-compose.onprem.yml), and every automatic path has a manual equivalent that always works.

Layered discovery — tried in order

#MechanismWhy it is here
1Remembered addresscovers the steady state; discovery is a first-run and recovery problem
2UDP broadcast beaconprimary — one ANNOUNCE⇄OFFER exchange solves both directions at once
3mDNS _crusaders-box._tcpinterop — any Bonjour browser proves "the board is fine, the API can't hear it"
4Subnet sweep (~12 s)the only layer that survives an AP with multicast filtering on — a shipped-enabled router checkbox
5Manual entryalways available — an automatic path that sometimes works is worse than a manual one that always does

Packet format

CRSDR1 <VERB> key=value key=value ... *CC\n

Same shape as the serial protocol, one mental model for both links. Limits: ≤12 fields, key ≤8, value ≤64, datagram ≤320 bytes. Empty value = bad_frame (absent and blank are different statements). Error precedence: bad_frame → bad_magic → bad_checksum → bad_verb → duplicate_key.

ANNOUNCE / OFFER

ANNOUNCE (box → broadcast): every 5 s unclaimed, 60 s claimed, and on link-up. Carries mac hw fw mega st n cch|dev+ten up sig. OFFER (API → unicast): url t n sig — the nonce echo kills replay across boots, and a claimed box refuses any unsigned or bad-signature OFFER, or anyone on the club WiFi could redirect a board to their own mainframe by answering faster. The t field is the API clock: a provisioned box adopts it once the HMAC has verified (its clock-recovery path after a power cut); an unclaimed box's offer is unsigned and its time is never adopted. A provisioned box also never repaints CLAIM CODE over its idle screen on a Mega reset or WiFi reconnect (review A2-7).

Protocols · Wire format №3

Device API — five signed calls, one identifier

Everything under /api/v1/device authenticates with the Device scheme — an HMAC over a canonical request string, never a JWT — and every call is box → API. Provision is the one anonymous exception, authenticated by the claim code instead. Request and response shapes are pinned in the shared corpus (src/contracts/device-protocol/http/cases.json: 16 signed-request vectors and a responses section) that both the C++ and the .NET suites assert, so neither side can drift without the other going red.

Identification — the 12-character access code

The 60-second JWT QR is retired from identification entirely: the Mega's frame codec caps an argument at 24 bytes and poisons anything longer, so the multi-hundred-byte HS256 token was dropped as TooLong at the panel every time (review H2). What the phone now puts in front of the scanner is an AccessCode: 12 upper-case Crockford base32 characters (no I, L, O, U — readable off a screen, typeable at a desk), 60 bits of CSPRNG entropy, a random handle to a tenant-scoped row that is the proof. Two purposes: a booking-activation code, minted in the booking's own unit of work and live until slot end + grace — it names its booking, so the box finds the roster entry with no search; and a short-lived member-ident code for walk-ups and the payer override. A code minted at one club resolves to nothing at another, structurally, through the tenant query filter. Bookings that predate codes are minted lazily by the roster builder and the QR screen from one rule.

Member surface: POST /api/v1/me/qr/generate returns {code, kind: booking|ident, expires_in_seconds, …}, and the PWA's /court-code screen renders the bare code as a QR through an in-house encoder (verified against python-qrcode, 40/40 identical matrices) — nothing but the 12 characters ever reaches the 24-byte pipeline.

Late evidence reverses a settled no-show (C6 residual, landed 2026-09-04)

Decision recorded in memory/decisions.md; mechanism in DeviceEventEndpoints.SettleAsync. A box offline longer than the grace window lights the court from its roster and queues the scan; by the time WiFi returns the sweep has settled the booking as a no-show, refunded it less the penalty and released the court. The upload used to resolve to not_chargeable — the member who played kept the refund and paid the penalty. Now BookingService.ReverseNoShowAsync posts two new rows, never an edit — a debit reversing the refund, a credit reversing the penalty, each the same type as the row it reverses with the opposite sign, referenced noshow-reversal:{booking}:{refund|penalty} — and the row goes back to Booked, checked in at the scan. EndsAt stays truncated (the tail may have been resold); the reversal posts whatever the balance (a correction, not a purchase). Outcome reversed_no_show, event booking.no_show_reversed. Offline scans are judged at scan time: the code's liveness and the cue gate use OccurredAt, derived from uptime arithmetic and clamped to the upload (with a device.event_time_clamped audit row) when a reboot made the box's counter wild.

Tenant settings the box runs on

The six court-box numbers that were hardcoded around the codebase are tenant_settings keys with one canonical default each, bounds-checked on the admin surface: walk_up_max_minutes (90, the relay cap), heartbeat_seconds (60), activation_forward_window_minutes (120), activation_cue_window_minutes (10), qr_lifetime_seconds (60, ident codes), roster_window_minutes (120).

Server side · Eventing

Webhooks, web servers & the SSRF guard

Every system event fans out to user- and admin-registered HTTP endpoints, HMAC-signed and retried per-endpoint. Webhooks are a programmatic mirror of the event stream — every player-affecting event also sends an email, never a substitute. Lights actuation is deliberately not on this bus: the webhook dispatcher is a store-and-forward worker with a 10 s timeout, wrong for a request-path relay flip — and the court box has no inbound HTTP listener at all, so it can never be a webhook destination. Actuation is the box's own decision, made through the device API; booking.lights_on / lights_off here are a mirror of what already happened.

Delivery semantics

Orderingat-least-once; receivers idempotent on event id
SignatureX-Crusaders-Signature: sha256=<hex> (HMAC-SHA256 of raw body)
TimestampX-Crusaders-Timestamp — reject >5 min old (replay)
Timeout10 s per attempt; per-endpoint queue so a slow endpoint blocks nobody
Retry sweepWebhookRetryWorker every 30 s, batches of 50
Give-upafter 6 failures: endpoint auto-disabled + owner emailed
Log retentionstatus, latency, retry count — 30 days, admin-visible

URL templating

http://box.local/court/{court_number}/turn/on

Single-brace placeholders resolved per-event from the payload — one config covers every court; adding court 5 is a database row, not a webhook change. Variables always available: tenant_id · tenant_slug · event_id · event_type · occurred_at(_unix) plus every flattened data key. Validated at save-time against the endpoint's event filter. A variable in the host is refused — payload fields carry member-supplied values, and a host assembled from those is a destination nobody chose.

SSRF guard — decided at the socket

Implemented in OutboundAddressGuard inside the socket's ConnectCallback, against the address about to be dialled — registration-time checks can't survive DNS rebinding. Refused unless allow-listed: loopback, RFC1918, link-local 169.254/16 (the cloud-metadata range an RFC1918-only guard misses), CGNAT 100.64/10, multicast/reserved, IPv6 equivalents, and IPv4-mapped IPv6 unwrapped before classification. Every resolved address must pass; redirects are never followed.

The LAN carve-out — do not close it

Webhooks:PrivateNetworkAllowList is CIDR-scoped — 10.0.40.7/32 admits one LAN consumer, not the private internet. AllowPrivateNetworks (guard off wholesale) defaults on in Development only.

Scoping

Player endpoints (≤5): only events where the player is subject or actor. Tenant-admin (≤20): all tenant events. Platform-admin: cross-tenant, for the observability stack.

Invariants — violating any is a defect

  • Money is ledger-only. Balance = sum of immutable entries, never a stored field. Every movement carries actor, subject, reason, external reference; disputes replay the ledger.
  • Credits are the unit of account. ZAR exists only on PendingTopup for reconciliation. A field mixing units is a money-correctness bug.
  • Charge at booking; refund on cancel; nothing back once checked in. Booking row + BookingCharge debit flush in one unit of work — a lost slot race can't leave a member paying for a court they didn't get. Penalty and refund post as separate rows, never netted.
  • Attendance means CheckedInAt — never the clock, never ChargedAt. A no-show is the absence of an identification match in the grace window. A box's queued activation is an identification match, judged at scan time.
  • The cue window gates the stamp. The 2-hour forward window only disambiguates back-to-back slices; CheckedInAt and the lights cue happen only from activation_cue_window_minutes (10) before start — a curious scan at 17:00 for an 18:45 slot answers too_early and forfeits nothing (review A2-11).
  • Every debit takes the payer advisory lock. PayerLock.BeginAsync serialises the read-then-post on the booking path and on both ChargeOnActivation branches — the payer reassignment and the never-charged row — so two courtside "I'll pay" taps cannot both see 200 credits and both post (review A2-10).
  • A settled no-show frees the slot. The sweep truncates EndsAt to its own clock in the same save as the refund and penalty, so the tail is resellable through the real GiST exclusion constraint, which exempts only Cancelled (review H5). No un-no-show admin endpoint; ledger adjustment is the recovery path — and a box's own late evidence is the one automatic exception (C6 residual).
  • One ordered candidate list, three touchpoints. QR, PIN and biometric all read CandidatesAsync ordered by StartsAt — the biometric path had its own unordered query and the documented two-bookings wrong-row bug was still live there (review H4) — and the biometric kiosk now sees the ActivationResult (insufficient balance et al.) instead of a plain "matched" (A2-9).
  • One box, up to four courts, and the list order is the wiring. Device.CourtNumbers is an ordered int[] whose position is the relay index; the button map is validated against its length at admin save time on every surface (ButtonMap.FirstSelectionBeyond), never logged per heartbeat.
  • Tenant isolation is structural. tenant_id on every entity; leakage is a P0 incident.
  • Admins act on behalf of users — every action representable as {actor, subject} in the audit trail.
  • Every configurable number is tenant_settings.<key>.
  • Every player-affecting event emails. Webhooks mirror, never replace.
Server side · Data

Database — PostgreSQL 16, ledger at the centre

Multi-tenant by column, not by schema: every row carries tenant_id and every endpoint resolves tenant first. The ledger is append-only; schema changes require an EF migration — EnsureCreated is not a strategy for a money-handling system.

Booking economics (as decided)

  • Default slice 15 minutes; 1-hour-per-day cap per member, relaxed same-day if courts are otherwise empty.
  • Charge at booking (2026-08-22 decision) — cancel refunds in full, less the late-cancel penalty inside the window; no refund after check-in.
  • Walk-ups create real bookings, truncated at the next booking and charged pro rata — which is why they need the network. Capped at min(walk_up_max_minutes, the 90-minute relay constant); idempotent on the box's purchase nonce.
  • A no-show settles as refund-less-penalty and releases the court (EndsAt truncated at the sweep); a box's late attendance evidence reverses the settlement with two opposite-signed rows, and the wallet report counts debits only so the reversal never reads as a second penalty.
  • Top-ups in R100 blocks, capped at R1000 for non-admins.
  • Reports: monthly presets + per-member spend drill-down; 2-year retention with anonymisation.
Server side · Money in

Payments — PayFast hosted checkout + ITN

The member never types a card number into anything this project serves — PCI scope stays a redirect. The redirect is not the notification: the server-to-server ITN is what moves money; the return URL only decides which screen the member sees.

Edges · Ship it

Deployment — one machine at the club

Standard FrostAura pattern: push → CI gates → multi-arch images → Docker Hub → Portainer API redeploy. The deploy target is the same physical machine that has the peripherals attached, reached from the internet only through a Cloudflare tunnel — no inbound ports.

The firmware release half — from iot-sign to a heartbeat's ota object

iot-sign (CI)

After iot-build proves every target compiles, iot-sign materialises OTA_PRIVATE_KEY (PEM content → 0600 file under $RUNNER_TEMP, rejected loudly if openssl cannot parse it), rebuilds court_bridge so the post-build hook appends the RSA trailer, derives the version from platformio.ini's FW_VERSION flags, and packages court_bridge.signed.bin + firmware.manifest.json ({version, url, sizeBytes}) as a 90-day artifact. With no key: a README plus a workflow warning — never a silent skip. One corpus-check gate (make corpus-check) runs in the iot job, so an edited cases.json with a forgotten regeneration goes red instead of leaving the C++ suite green against old vectors.

Baked into the API image

Both backend image builds download the artifact into firmware-payload/ and the Dockerfile copies it to /app/firmware/ (a tracked placeholder README keeps local compose builds working). Program.cs serves that directory at /firmware/ — anonymous, .bin/.json only, no listing, no traversal, a tenantless prefix so a miss is a 404: the box cannot sign a GET, and the RSA trailer is the integrity anchor.

OtaCatalogue offers it by default

Stable falls back to the image's own firmware.manifest.json when Ota:Stable:* is unset, so a deployed image offers its own firmware with zero config; explicit config still wins (how a fleet is pinned to another image). The ESP8266 HTTP client refuses a relative URL before a packet leaves the board — CI's manifest and .env.example both carried that latent dead-on-arrival — so the catalogue composes an absolute URL: Discovery:AdvertisedBaseUrl → the scheme and host of the heartbeat that is asking → PublicBaseUrl. The heartbeat then carries ota{ota_version, ota_url, ota_size}, omitted when the box already runs or has condemned that version.
