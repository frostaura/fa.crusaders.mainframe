System · End to end

Topology — from tap to relay coil

Everything runs on one on-prem machine at the club behind a Cloudflare tunnel; the court box and one small ESP32 controller per door are the only other computers. The API never dials the box — every call is box → API, carrying the club’s single device API key as Authorization: Bearer and the box’s MAC in the body. A scan asks POST /api/v1/device/activate first and is decided from the heartbeat-pushed roster only when the API could not be asked; the mains-side safety timer lives one hop further down, on the Mega itself.

Online first; the court still works when the network does not

A scan asks the API — only it knows about a booking made thirty seconds ago or a balance too low to admit — and its answer is final. When the API cannot be asked (no link, no court list yet, the circuit breaker open, a 5xx, a malformed 200) the box decides from the roster the last heartbeat pushed, and the API hears about it later via the sequence-numbered event queue.

Charge at booking — decided 2026-08-22

Booking posts the BookingCharge debit in the same unit of work as the slot. Supersedes the blueprint's charge-on-lights-on; committee sign-off pending.

Two fail-safes point opposite ways — on purpose

The relay timer fails open (lights off even if everything above dies). The roster cache fails closed (a stale roster refuses entry). Both are correct.

Hardware · Overview

The court box

A WeMos Mega 2560 with its onboard ESP8266, driving four court-light relays, a 20×4 2004A LCD driven as 20×4, an eight-button panel and a QR scanner. The wiring is fixed and cannot change — every pin, serial port, baud rate and DIP position below reflects hardware already built and working. Firmware adapts to the hardware, never the reverse.

Why the brains live on the ESP8266

The ATmega2560 cannot be flashed over WiFi: its ESP8266 sits on Serial3, not the Serial0 bootloader port, and no GPIO reaches the Mega's RESET pin — adding one would be a wiring change. So the split is deliberate:

Ownsbuttons, scanner framing, relay drive, the LCD — the landing screen, every screen’s deadline, the live court row, the hint row, and the CHECKING YOUR CODE it paints itself on every scan so a dead ESP is visible on the glass — and the independent auto-off timerprotocol, device auth, heartbeat, the scan decision (lib/bridgelogic: online-first, roster fallback), !AUTH arming, !STATE reconciliation, roster cache, event queue — and the words on every screen, because verdict wording is exactly what a club changes its mind about and the Mega is the half that needs a screwdriver
Updated byUSB, rarelyUSB too — the Arduino IDE, whenever a value in secrets.h changes. OTA was removed at firmware 2.0.0: a fleet-update mechanism for one box is a way for the box to break itself and nothing else

In the system this replaces, the off command was scheduled inside an Excel macro on a Windows PC — close the workbook mid-session and a court burned until somebody noticed. The Mega's timer is independent precisely so that if the ESP hangs, WiFi drops and the backend dies, the lights still go off. The screen-revert deadline moved to the Mega for the same reason, and that is the whole argument for it: the ESP is the half that goes away, so a timer that rescues the glass from a stuck screen is useless on the half whose crash left it stuck. A refusal screen that never left the panel, with every button dead behind it, is a failure this box has actually had.

⚠ Relays — open safety question, gates go-live

The relay module is rated 10 A @ 250 VAC. Plausible for one modern LED court bank; inadequate for older metal-halide. Standard practice is relay → contactor coil, contactor carries the lighting load. Not yet confirmed on the installed hardware. If relays switch lighting directly, a qualified electrician is required before anything ships. No software decision changes this.

The display is a 20×4, driven as 20×4

The panel always was a 2004A and the firmware now uses all of it. No wire changed — two build flags did (LCD_COLS/LCD_ROWS), and court::kLineLen is derived from them. That derivation is the fix: the width was hardcoded at 16 while the flags said otherwise, so four columns of every line were unreachable on the glass that is actually fitted. What makes widening it safe is a contract, not a flag: rows 0–1 cut at column 16 must still be a complete message on every screen, so a 1602 fitted by mistake degrades to exactly the old behaviour rather than to half a sentence. Rows 2–3 and the columns past 16 carry enrichment only. Somebody still has to look at the fitted panel before a club box is flashed.

Hard limits burned into the Mega

RELAY_HARD_CAP_MS = 90 min — no frame can express indefinite-on, and the same 5400 s is now one constant on both sides: proto::kRelayHardCapSeconds (static-asserted in the ESP build too) and the backend's RelayHardCap, pinned by the buttonmap corpus, so the button map, a walk-up and an activation can no longer sell minutes the relay will not deliver. AUTH_TTL_MS = 30 s — button authorisation expires. Both hold regardless of what the ESP, network or backend believe.

The box carries no clock at all — and that is the fix, not a gap

Review C1 found a box that had to sign every request with a wall clock it had no way to seed. The whole apparatus that grew around that — server_unix in a provision response and in every heartbeat, a 401 body carrying the server clock so a clockless board could recover, an asymmetric skew window, a two-strike loop breaker, a clock adopted from a verified discovery OFFER — is gone, because with one static key there is nothing to sign and nothing to date. The box keeps only tb::Uptime64, a 64-bit accumulator over millis(). The heartbeat's uptime_ms and both uptime_ms fields on an events batch are rendered from it, and the server dates an event from the difference between the two. A uint32_t anywhere on that path is the 49.7-day wrap re-entering through the API, and it once was: an activation queued before the wrap and uploaded after it arrived stamped 49.7 days ahead of its own batch.

Event queue

A RAM ring of what the box did — Activation · Release · UnknownScan · Fault · Boot — drained to the API when reachable, at most 32 per batch. Survives WiFi loss, router reboots, a two-day outage; not a power cut. That last one is now stated honestly: the store's value cap went 32 → 128 bytes and a 48-byte Event would fit, so persisting the ring has not been built rather than being impossible — it needs a record per slot plus a durable head and tail, and a torn ring that replays a stale activation charges a member twice. The sequence number does persist, in blocks of 64, and is the only thing left in flash: API-side deduplication is a permanent unique index on (tenant, device, seq), so a box that restarted numbering at 1 would have every event receipted as a duplicate. Only the roster path queues: an activation the API itself granted is one it already recorded. A queued activation is evidence, not a charge — it is what stops the no-show sweep reversing a debit already posted at booking (review C6).

The rollover rule

millis() wraps every ~49.7 days and a box in a cupboard is normally up that long. Never compare times directly — use tb::reached(now, deadline) / tb::Deadline. The predecessor firmware got it wrong in both directions on adjacent lines (0-as-sentinel, and now >= expiresAt — false for 49.7 days after the wrap, so the relay was never released). make lint-iot greps for raw deadline comparisons outside lib/timebase.

Flashing — both halves, over USB, and nothing else

Four values

A box knows exactly what is compiled into it. secrets.h (gitignored, all four mandatory — the bridge #errors without them and static_asserts on an empty one) holds WIFI_SSID, WIFI_PASSWORD, API_BASE_URL — the gateway's LAN address and port, http, never https, because the box has a plain WiFiClient and no heap for a TLS context — and DEVICE_API_KEY, read off the admin Devices page. Rotating the WiFi password, the key or the base URL is the same procedure for all three: edit the file, upload court_bridge, restore the run DIPs.

The Arduino IDE is the route

Open arduino/court_mega, then arduino/court_bridge, press Upload for each; nothing to install from the Library Manager, because each sketch folder vendors every library it needs. Boards are pinned to what CI compiles against — Arduino AVR 1.8.6 and esp8266 3.1.2, matching the PlatformIO platforms. make flash-mega / make flash-bridge do the same two uploads from PlatformIO and are the developer alternative.

What went, and why

OTA, the RSA-2048 image trailer, BootGuard, the iot-sign job, the OTA_PRIVATE_KEY secret, the /firmware/ route, the Ota:* override and the flash credential store are all removed. The signing key never existed — the private half was unlocatable, so every board flashed with the committed public key would have rejected every image nobody could sign. One club, one box and a USB cable needed none of it, and each link in that chain could strand a board in a cupboard.

Protocols · Wire format №1

Serial protocol v2 — Mega ↔ ESP8266

9600 8N1 over Serial3, line-terminated, NMEA-style XOR checksum. v2 exists because the legacy protocol had two defects that can't survive being driven by a server: ON had no duration (the off command lived in a VBA macro on a Windows PC) and no integrity (a corrupted a arriving as A turns lights on and leaves them on). v2 is additive — the codec still speaks every legacy verb in both directions — but the production Mega does not: court_mega constructs its decoder with LegacyDialect::Refuse, so any downlink line not beginning with ! is answered !EVT,BADFRAME,RX and moves no relay. The bare A was the one message that closed a relay with no checksum, on a UART that receives the ESP's 74880-baud boot banner at every ESP reset. The simulator opts into Accept, because it is the bench.

Seconds are clamped, never rejected (saturating, not wrapping): a clamped light is a wrong-length game; a rejected one is a dark court. AUTH clamps 0–5400; ON/EXT clamp 1–5400 — zero is an OFF wearing an ON's clothes. SHOW clamps 1–120, and the two ranges are separate fields rather than one constant because they bound different things: a relay duration by the ninety minutes that stop an unattended court burning, a screen hold by the two minutes that stop a screen becoming permanent. One constant serving both would have let a !SHOW,5400 stand on the glass for an hour and a half.

The verb table is append-only. Four verbs were added by appending, because the grammar table is indexed by the verb’s value — a row in the wrong place would silently give every verb someone else’s grammar, and ON would inherit OFF’s arity and lose the mandatory duration that v2 exists for. A compile-time check fails the build instead. Never reorder, never insert.

The two safety rules live on the Mega

1 — Every ON carries a deadline. v2 cannot express indefinite-on; RELAY_HARD_CAP_MS (90 min) caps even a frame that asks for more. A Mega whose bridge is unplugged still opens its relays. 2 — Authorisation expires. !AUTH arms buttons for a bounded window (30 s = AUTH_TTL_MS); the legacy authenticated flag had no expiry, so a button pressed hours after someone else's scan fired a relay on their account. Review H1 found the bridge never sent !AUTH, so every button press was discarded. Who the window is for is bridgelogic::AuthPolicy's rule, and it matters as much as the expiry: it arms only for a scan somebody recognised — the API answered with a verdict about a known member, or the roster matched an entry — so an unknown barcode arms nothing. And a grant does not close the window, it binds it: the court that just lit is remembered, the window stays armed for the same TTL, and an OFF press is honoured for that court only (NOT YOUR COURT / SCAN TO START otherwise). Before this, any barcode bought thirty seconds of buttons — and with an admin-mapped OFF button, a stranger could dark a league match — while the paying member's own grant closed theirs.

Protocols · Who the box is

Identity & flashing — one club key, and a box that introduces itself

Device authentication is the whole of one sentence: one static per-club API key, presented as Authorization: Bearer, with the box's MAC in the request body. No signature, no canonical string, no nonce, no timestamp, no clock window, no per-device key, no provisioning call, no discovery. A key the API does not recognise is a bare 401 with an empty body; a MAC it does not recognise registers itself.

Getting a box onto a court

#Step
1Read the club's device API key off the admin Devices page. It is readable, not shown-once, because an admin has to paste it into a secrets.h at a workbench weeks after the club was created.
2Paste it into arduino/court_bridge/secrets.h beside the other three values.
3Open arduino/court_mega and then arduino/court_bridge in the Arduino IDE and press Upload for each (DIP positions).
4Restore the run DIPs, power-cycle, screw the box to the wall.
5It appears on the Devices page by itself on its first heartbeat.

Regenerating the key on the Devices page invalidates the old one on the very next request — nothing is cached, because a cache with any lifetime at all is a window in which a rotated-away key still works. So a regeneration is a reflash of every box, and the page says so.

Auto-registration is the whole of provisioning

DeviceRegistryService.AutoRegisterAsync creates the row from nothing but the MAC. device_code is box-<last six hex of the MAC> — what an admin reads off the board's label — falling back to the full MAC if that code is taken, because device_code is uniquely indexed and a collision would otherwise throw at the one moment nobody is watching, a box registering itself at 6am. The guesses are the ones an admin would otherwise type: the club's courts in ascending order, up to the four the relay bank drives; the club's button map, trimmed if it selects a court this box has not got. The row is flagged AutoRegistered, the Devices page badges it “New — check court numbers” until an admin edits it, and an audit row is written with actor Guid.Empty — nobody did this.

Why a key at all, when both ends are on the club LAN

Because the backend's public surface is a Cloudflare tunnel — that is how members book and how the admin runs the club remotely — so /api/v1/device/* is internet-reachable, and the key is what stands in front of it. Nothing in the firmware assumes the box is ever off the LAN, and nothing assumes the API is LAN-only. The comparison is constant-time and the lookup is a linear pass over the clubs that hold a key with no early exit on a hit, so the response time cannot say which club matched.

What this replaced — all of it removed

A UDP discovery listener on 48653 needing host networking to hear a broadcast · ANNOUNCE / OFFER · a claim code read off the box's LCD · a commitment hash · a provisioning grant · a one-shot per-device key derived from a master KEK · key rotation, re-claim and revoke · an HMAC over a canonical request string · a nonce cache · a two-minute clock window · a 401 body carrying server_unix · the 16 signed-request corpus vectors. Every link in that chain could strand a board in a cupboard, and all of it existed to protect a per-board credential that one club with one box does not need.

The two identity screens, and there are no others

CONNECTED / SCAN TO START — the box is on the club WiFi. CRUSADERS COURTS / SCAN TO START — it is not, and that is deliberately the same wording the Mega paints when idle, because the court still works offline from the roster and the glass should not shout an error at a member who can simply scan. Both are painted at the end of setup() and again on the first !PONG of the boot. There is no claim-code screen, because there is nothing to claim, and no WiFi-provisioning screen either: !WIFI was a verb of the serial protocol until firmware 1.2.0 and is not one now.

Protocols · Wire format №2

Device API — five calls behind one club key

Everything under /api/v1/device authenticates with the Device scheme — the club's one API key as Authorization: Bearer, never a JWT — and every call is board → API. The scheme authenticates a club, not a board: which board is calling is the mac in the body, and what kind of board it is is the row that MAC resolves to. There is no anonymous call and no sixth one: provisioning is gone, and an unknown MAC on a heartbeat registers itself. Four of the five are the court box's; the fifth, /gate, belongs to the door — and each kind is refused by name on the other's paths rather than by the accident of an empty court list. Request and response shapes are pinned in the shared corpus (src/contracts/device-protocol/, http/ for the box and a separate gate/ family for the door) that both the C++ and the .NET suites assert, so neither side can drift without the other going red — and the anti-drift rule is an executed-case count, not a checksum, because a side that skips what it cannot parse passes a checksum and fails in the field.

Dating an event without a clock

The box carries no wall clock, so an offline scan is dated by uptime arithmetic: the batch's uptime_ms minus the event's, subtracted from the moment the upload lands. Both are rendered from the 64-bit accumulator, so the 49.7-day millis() wrap cannot re-enter through the API. Offline scans are then judged at scan time, not upload time — the cue gate, CheckedInAt and the roster code's liveness all use that instant. Only a future time (the queue outlived a reboot) or one past a 30-day sanity bound is clamped to the upload and audited device.event_time_clamped. The earlier six-hour clamp, sized to the roster's trust window, re-created the very failure it was meant to prevent for any outage longer than six hours.

Identification — the 12-character access code

The 60-second JWT QR is retired from identification entirely: the Mega's frame codec caps an argument at 24 bytes and poisons anything longer, so the multi-hundred-byte HS256 token was dropped as TooLong at the panel every time (review H2). What the phone now puts in front of the scanner is an AccessCode: 12 upper-case Crockford base32 characters (no I, L, O, U — readable off a screen, typeable at a desk), 60 bits of CSPRNG entropy, a random handle to a tenant-scoped row that is the proof. Two purposes: a booking-activation code, minted in the booking's own unit of work and live until slot end + grace — it names its booking, so the box finds the roster entry with no search; and a short-lived member-ident code for walk-ups and the payer override. A code minted at one club resolves to nothing at another, structurally, through the tenant query filter. Bookings that predate codes are minted lazily by the roster builder and the QR screen from one rule.

A booking-activation code never identifies a buyer or a payer. IdentificationResolver returns a user only for a MemberIdent code; a booking code is usable only through /activate, for its own booking. A roster code travels in clear on the LAN and sits in box RAM for hours, and it was briefly accepted as a global identity for walk-up purchases and the “I'll pay” override — so anyone who read one could buy court time with that member's minutes at any box. This is what keeps the stolen-box threat model true: nothing the box holds is a member's identity.

Member surface: POST /api/v1/me/qr/generate returns {code, kind: booking|ident, expires_in_seconds, …}, and the PWA's /court-code screen renders the bare code as a QR through an in-house encoder (verified against python-qrcode, 40/40 identical matrices) — nothing but the 12 characters ever reaches the 24-byte pipeline.

Late evidence reverses a settled no-show (C6 residual, landed 2026-09-04)

Decision recorded in memory/decisions.md; mechanism in DeviceEventEndpoints.SettleAsync. A box offline longer than the grace window lights the court from its roster and queues the scan; by the time WiFi returns the sweep has settled the booking as a no-show, refunded it less the penalty and released the court. The upload used to resolve to not_chargeable — the member who played kept the refund and paid the penalty. Now BookingService.ReverseNoShowAsync posts two new rows, never an edit — a debit reversing the refund, a positive row reversing the penalty, each the same type as the row it reverses with the opposite sign, referenced noshow-reversal:{booking}:{refund|penalty} — and the row goes back to Booked, checked in at the scan. EndsAt is restored to the original end (or the earliest surviving overlap's start) and any booking sold into the released tail that nobody checked in on is displaced — cancelled with its charge or penalty returned, reason ResoldTailRefunded, audited and emailed; the reversal posts whatever the balance (a correction, not a purchase). Outcome reversed_no_show, event booking.no_show_reversed. Offline scans are judged at scan time: the code's liveness and the cue gate use OccurredAt, derived from uptime arithmetic and clamped to the upload (with a device.event_time_clamped audit row) only when it lies in the future or beyond a 30-day sanity bound — a two-day outage's evidence still resolves at scan time, and booking codes outlive that horizon.

Doors · The second device kind

The door gate — one ESP32, one lock, one lamp

A member holds their phone up to a scanner, the lock releases for a few seconds, and that is the whole product. It is the court box's shape with the money taken out — the same club key, the same /api/v1/device group, the same rate limit (a bucket per board), the same auto-registration, the same roster grammar — and it is pull-only for the same reason the box is: no listening socket, no static IP, no WiFi.config(), a DHCP lease and nothing else. The sketch it replaces ran an unauthenticated HTTP server on the board whose /open endpoint unlocked the door for anyone on the club WiFi. One image serves every door: nothing per-gate is compiled in, a door is named in the admin console, and the board never needs to know its own name — so a spare board is a spare board rather than a board for one particular door. The behaviour oracle is docs/specs/door-gate.md; the flags and the loop are src/iot/door-gate/README.md.

⚠ What the door does with no power is unmeasured — and this firmware has never run on hardware

The owner's stated default is that the door is released when the power is out. Two different failures hide in that sentence and the software creates neither. A power cut takes the lock's own supply with it, so what the door does is decided by the lock: a fail-safe lock — held shut by current — releases, a fail-secure one stays shut, whatever any flag says. A dead or resetting board with the lock's supply still up only de-energises the relay coil, and GATE_UNLOCK_ENERGISES_RELAY alone decides that case. Which lock is fitted, and which relay contact feeds it, are recorded nowhere in this repository — so nothing here claims an answer to either. Both are measured on the go-live bench with a meter and an audible lock, and Carl is asked the two facts (docs/go-live-checklist.md §12).

Egress is mechanical, and is not this board's job

Getting out of the building must not depend on this system at all — not on the ESP32, not on the relay, not on the API, not on a scan, and not on the power being on. A panic bar or a mechanical handle is a building-code requirement and a physical one. Nothing in this repository is a life-safety device, nothing here is rated or certified as one, and no combination of the flags turns it into one. Everything on this page is about entry; the corollary is that a gate which is wedged, unpowered, unreachable or refusing every scan is an inconvenience and never a trapping hazard.

What the lamp means

Solid — the lock is released, push the door. Three fast blinks — refused. Slow 1 Hz — the radio is not associated and the board is deciding from its roster. Two quick blinks — it has just booted. Solid beats everything, so the second member of a pair, refused while the first one's window is still running, sees a steady lamp rather than the refusal blinks: the door is open in front of them, which is the truer and more useful thing for the lamp to say. That is on the bench list so the person testing expects it instead of reporting a dead LED.

The watchdog number is the one that was wrong and is the reason the assertion exists. It was exactly one worst-case call, which against an API host that silently drops packets is a guaranteed reset loop: the board panics before the call it is waiting on can return, boots, heartbeats, and does it again — never loading a roster and admitting nobody. A call is three separate budgets and one call can spend all three, which is the trap the single number hid: the TCP connect, the status line and headers, and the response body, four seconds each. Twelve was right for a two-phase call; the body got its own budget when sharing one with the headers left a 4.6 KB roster no time at all on a slow evening, and the assertion moved with it.

The two release bounds are different numbers with different jobs, and used to be the same number by coincidence. The default is how long a member is given to get through a door — longer is kinder, and the cap is what stops it being unsafe. The dwell is how long a door somebody has held open for the whole cap has to stay shut — longer is a queue of innocent members refused for something one person did. Raising the default to fifteen seconds did not move the dwell, and a later edit that re-collapses them fails a test.

Offline, the roster is the fallback and nothing else. Fifteen seconds buys one extension, not nine. The thirty-second cap bounds the whole opening, measured from the moment the door first released, not each answer — so a longer grant spends more of that budget per scan. A booking code is not a standing building key. Unbounded, the code a member's phone showed them at 17:00 for a 19:00 court opened every door in the club at 03:00 the same night, for as long as the row survived. It is now bounded by its own booking's window under every policy: early entry under booking_window, and under active_member the horizon in which the member's own phone would show them that code at all — the roster window plus the lights-on cue — never narrower than what the cached roster already admits, and never wider than 240 minutes, with all three settings clamped as they are read so a hand-edited settings row cannot widen a door. After it: not_recognised, deliberately indistinguishable from a code that never existed.

Two consequences that took a round to get right. A booking the sweep has already marked a no-show still opens the door while its code is live — being swept as absent from a court must not lock a member out of the building; so does one the lights worker has marked completed, because the only thing that completes a booking is its holder having turned up; only a booking the club itself cancelled or blocked opens nothing. And a member holding an earlier, spent code still gets in while they hold another live booking whose door window contains now, because the door's question is "may this person come in", not "is this the newest QR on their phone".

The policy is the one setting in this tree that fails closed

Everywhere else — the button map, the club's opening hours — a settings document somebody has broken falls back to something permissive, because the alternative is a club whose courts stop over a typo with nobody to ask. A door is the other way round. The two failure modes are "a member is sent to the desk" and "the building is open to whoever holds any live code", and only one of those is recoverable by a person: so an absent key is the documented default, and a present but unreadable one reads as the narrower policy. The admin save validates strictly and, when it refuses, writes nothing at all.

A door is never attendance — the single most important sentence about it

A member coming through the front door may be collecting a racquet, watching somebody else's league night, arriving an hour early for a court they then cancel, or leaving. Nothing about an open licenses an inference about a court. So a gate never stamps CheckedInAt, never reverses a no-show, never charges lit time and never writes a ledger row — not as an omission to be filled in later, but because there is no court to attribute any of it to. It is therefore invisible to the settlement model, and a silent door darkens no court and waives no penalty. Expect this to be argued with the first time somebody wants entry statistics: the answer is that the audit rows are the statistics.

What this does not claim

A cut-off door goes on admitting

Taking a door out of service takes effect at the server immediately and at the board only when the board next asks. One that has been cut off — uplink pulled, switch dead, line down — never hears the 403 and goes on admitting whatever its cached roster still carries, until that roster goes stale six hours after it was last received. No firmware can close that window. "Out of service" is not a lock; where a club needs a door shut now and cannot reach the board, the answer is physical. Whether six hours is the right ceiling is an open question for the owner, not a technical one.

Offline is rostered bookings and nobody else

Under the default policy an active member with no court booked gets in online and does not get in offline. That is stated rather than engineered around: the alternative is pushing the club's entire membership roll to a board in a doorway, which is a different product and a far worse secret to leave in a cupboard. Two edges of the same shape: a club with more than forty-eight bookings inside the window leaves the forty-ninth off the roster, and a booking whose status changes after a push is only as current as the next one. An unnamed board has no degraded mode at all.

A court box's roster is a door key too — open

The wire is cleartext HTTP on the club LAN, as the court box's already is, and codes are bearer tokens: a member who shares a QR shares entry for that window, and nothing on the server or at the door can tell the difference. An audit row names whose code it was, which is not a claim about who walked through. The unclosed edge is that a court box heartbeat still hands a key-holder live booking codes for its courts with no naming step at all — and after this change those codes open doors inside their window. The door's naming gate protects the door's roster only. Should an auto-registered, never-acknowledged court box also get no roster? Owner's call.

Server side · Eventing

Webhooks, web servers & the SSRF guard

Every system event fans out to user- and admin-registered HTTP endpoints, HMAC-signed and retried per-endpoint. Actuation is the box's own decision, made through the device API; booking.lights_on / lights_off here are a mirror of what already happened.

SSRF guard — decided at the socket

Implemented in OutboundAddressGuard inside the socket's ConnectCallback, against the address about to be dialled — registration-time checks can't survive DNS rebinding. Refused unless allow-listed: loopback, RFC1918, link-local 169.254/16 (the cloud-metadata range an RFC1918-only guard misses), CGNAT 100.64/10, multicast/reserved, IPv6 equivalents, and IPv4-mapped IPv6 unwrapped before classification. Every resolved address must pass; redirects are never followed.

The LAN carve-out — do not close it

Webhooks:PrivateNetworkAllowList is CIDR-scoped — 10.0.40.7/32 admits one LAN consumer, not the private internet. AllowPrivateNetworks (guard off wholesale) defaults on in Development only. It is configuration-file only, and empty by default. There is no admin screen for it and no API that reads or writes it, so moving a club’s LAN consumer onto the list today means editing appsettings.json and restarting the API. The carve-out exists and works; operating it does not yet.

Invariants — violating any is a defect

  • Money is ledger-only. Balance = sum of immutable entries, never a stored field. Every movement carries actor, subject, reason, external reference; disputes replay the ledger.
  • Whole minutes are the unit of account. A booking costs exactly its length, SliceMinutes × SliceCount; there are no court prices, group prices or conversion rates, and nothing holds a fraction of a minute. Every split, share and penalty rounds down in favour of whoever pays. Rand appears only where money changes hands — package prices, the purchase row (PendingTopup), the ledger's ZarPaid and the desk's amount received — for reconciliation, and never enters a balance. A field mixing units is a money-correctness bug, and a test fails on any *Minutes property typed decimal.
  • Charge at booking; refund on cancel; nothing back once checked in. Booking row + BookingCharge debit flush in one unit of work — a lost slot race can't leave a member paying for a court they didn't get. Penalty and refund post as separate rows, never netted.
  • Attendance means CheckedInAt — never the clock, never ChargedAt. A no-show is the absence of an identification match in the grace window. A box's queued activation is an identification match, judged at scan time.
  • The cue window gates the stamp. The 2-hour forward window only disambiguates back-to-back slices; CheckedInAt and the lights cue happen only from activation_cue_window_minutes (10) before start — a curious scan at 17:00 for an 18:45 slot answers too_early and forfeits nothing (review A2-11).
  • Every debit takes the payer advisory lock. PayerLock.BeginAsync serialises the read-then-post on the booking path and on both ChargeOnActivation branches — the payer reassignment and the never-charged row — so two courtside "I'll pay" taps cannot both see 200 minutes and both post (review A2-10).
  • A settled no-show frees the slot. The sweep truncates EndsAt to its own clock in the same save as the refund and penalty, so the tail is resellable through the real GiST exclusion constraint, which exempts only Cancelled (review H5). No un-no-show admin endpoint; ledger adjustment is the recovery path — and a box's own late evidence is the one automatic exception (C6 residual).
  • One ordered candidate list, three touchpoints. QR, PIN and biometric all read CandidatesAsync ordered by StartsAt — the biometric path had its own unordered query and the documented two-bookings wrong-row bug was still live there (review H4) — and the biometric kiosk now sees the ActivationResult (insufficient balance et al.) instead of a plain "matched" (A2-9).
  • One box, up to four courts, and the list order is the wiring. Device.CourtNumbers is an ordered int[] whose position is the relay index; the button map is validated against its length at admin save time on every surface (ButtonMap.FirstSelectionBeyond), never logged per heartbeat.
  • Owed is a function of the booking's terminal state alone, never of the order events arrived in — and never more than the price quoted at booking. The rules, their reasons and where each is enforced are in the settlement model, which is normative: where the code and that document disagree, one of them is a defect.
  • Tenant isolation is structural. tenant_id on every entity; leakage is a P0 incident.
  • Admins act on behalf of users — every action representable as {actor, subject} in the audit trail.
  • Every configurable number is tenant_settings.<key>.
  • Every player-affecting event emails. Webhooks mirror, never replace.
Server side · Data

Database — PostgreSQL 16, ledger at the centre

Multi-tenant by column, not by schema: every row carries tenant_id and every endpoint resolves tenant first. The ledger is append-only; schema changes require an EF migration — EnsureCreated is not a strategy for a money-handling system.

Booking economics (as decided)

  • Default slice 15 minutes; 1-hour-per-day cap per member, relaxed same-day if courts are otherwise empty.
  • Charge at booking (2026-08-22 decision) — cancel refunds in full, less the late-cancel penalty inside the window; no refund after check-in.
  • Walk-ups create real bookings, truncated at the next booking and charged pro rata — which is why they need the network. Capped at min(walk_up_max_minutes, the 90-minute relay constant); idempotent on the box's purchase nonce.
  • A no-show settles as refund-less-penalty and releases the court (EndsAt truncated at the sweep); a box's late attendance evidence reverses the settlement with two opposite-signed rows. Every one of these outcomes is stated normatively, with its reason, in the settlement model.
  • The club's opening hours are a booking rule, not decoration. tenant_settings.operating_hours carries a per-weekday "HH:mm-HH:mm" map; the grid draws each day from its own row and a booking outside that day's hours is refused. It is read leniently — a weekday the parser cannot make sense of is simply absent, and that day falls back to the flat default, because a hand-edited settings document must never close a club — and written strictly from the admin screen, where a bad row is named and refused while somebody is standing there to fix it.
  • The desk can put a member into the red, and only ever on purpose. A member short of the price gets the ordinary 402 insufficient_balance, carrying their balance and the price. An admin booking on that member's behalf may then re-send the request asking for the overdraft by name, and the booking goes through at the same price with the same BookingCharge — the wallet goes negative, the amount owed does not change, and the audit row records who authorised it. It is never implied by being an admin: the flag is honoured only when the actor and the subject are different people, so nobody can overdraw their own wallet with it and no member's own request can carry it.
  • A booking costs its length in minutes. Members buy admin-defined minute packages through PayFast — the club's packages, at their group's discount if one of their groups sets one, plus their own groups' packages — or the desk sells one. There is no spend cap, and bought minutes never expire.
  • Reports: monthly presets + per-member spend drill-down; 2-year retention with anonymisation.
Server side · The money statement

Settlement model — what a member owes, after any sequence of events

The money path had no single statement of itself, and five round-3 findings were five symptoms of that absence: each local fix was reasonable and they contradicted each other, so a played court could come out free, a court charged 100 could bill 143, a member who could have played was refunded and locked out, two members were charged for one court, and one member's desk adjustment suppressed another's settlement. docs/specs/settlement-model.md is now normative — where it and the code disagree, one of them is a defect, and you say which.

The statement

For every booking b with payer u, Owed(b) is a function of b's terminal state alone. Every event in the booking's life either changes that state or corrects the ledger towards the Owed of the state it is already in. No event adds a charge that is not one of the rows below. Owed is not materialised anywhere — there is no stored balance and there must not be one; it is a property of the rules, checked by pinning tests, not a column.

Terminal states

#Terminal stateOwed
S1Booked / Completed — attended, or not yet decidedP
S2Cancelled before check-in, outside the penalty window0
S3Cancelled before check-in, inside the penalty windowpenalty
S4Cancelled after check-inP
S5NoShow — swept, no attendance evidencepenalty
S6NoShow reversed by late attendance evidenceP
S7S2/S3 and the court was later lit on this booking's own codemin(P, prior + proRata(lit))
S8Displaced (ResoldTailRefunded)0
S9AdminBlock, or no usernot settled

P = AmountChargedMinutes, the booking's length in whole minutes, locked at booking, never recomputed from settings that may since have moved. S7 is the only state that composes: a retained late-cancellation penalty is part of what the member has already been billed, so lit time is netted against it and capped at P.

The two invariants everything else serves

I1 · Ceiling0 ≤ Owed(b) ≤ P in any sequence of events. The price was quoted and accepted at booking; everything after is a correction of who owes what, not a second sale. The finding this closes billed granted minutes plus a retained late-cancel penalty and reached 143 for a court charged 100.
I2 · No free courtIf a court was lit on a booking's identity, Owed > 0 unless an admin explicitly waives it. The club's electricity ran and the slot was consumed. I2 outranks precision — a release that never arrives leaves the grant as the answer, because deferring the charge would make a lost release a free court.

Grant is not measurement

An activation event carries a grant — what the relay was told to run for, an upper bound. The release that follows carries heldMs: what it actually ran, and the system's only measurement. So the lit window is bounded three ways, because each fails differently:

litEnd   = min(scan + grant, OriginalEndsAt,
               scan + heldMs   when the release has landed)
litStart = max(scan, StartsAt)
litMin   = clamp(ceil(litEnd − litStart), 0, min(M, 90))

A release names no booking, so it is paired by device, relay and time — the latest activation receipt for the same (device, relay), accepted only when the implied end sits within 2 minutes of the release's own time (both come off the same uptime accumulator). One that cannot be paired is audited device.release_unpaired and dropped: a release that corrects nothing is right, one that corrects the wrong session is not.

A hand adjustment is netted per leg, never read as a signal

An AdminAdjustment naming a booking is money that has already moved. Both legs of a reversal are always attempted, each netted against adjustments moving money in its own direction. The sign of a desk correction says nothing about which leg it repaired — reading it as “the desk already fixed this” made a played court free in one direction and charged the member twice in the other. An adjustment may only name the payer's own booking.

Displacement is eager, and reversed when the release disproves it

The two error directions are not symmetric. Displacing on a window the court did not use costs a wrongly-refunded member and a dark slot; not displacing on a window it did use puts two members on one lit court, both charged. So a booking overlapping the provisional lit window that nobody checked in on is displaced, refunded in full, its code expired, its member emailed — and reinstated if the release proves the court went dark before its start and it has not yet begun.

Two rows, never a netted one, and never an edit

A correction posts a new row of the same type with the opposite sign, reading what it reverses off the ledger rather than recomputing it from settings. A single net row cannot answer “how much penalty did I pay?”, which is the question a disputed settlement asks. Accepted consequence: a period bucket can go negative when a sweep and its reversal fall on different days. refunds_minutes and penalties_minutes are net figures; only penalty_count counts gross. And a posting of zero minutes is never written — it moves nothing and burns its idempotency reference.

Edges · Ship it

Deployment — one machine at the club, one published port

Standard FrostAura pattern as far as the registry: push → CI gates → multi-arch images → Docker Hub, where it stops by decision — the Portainer redeploy job was removed 2026-09-19, so redeploying the club stack is a manual step. The deploy target is the same on-premises machine the court box reaches over the club LAN, and the box speaks plain HTTP only — which is why the gateway is published on a LAN port and why nothing hands a box an https URL.

Three images, not two

The gateway used to be stock nginx:alpine with nginx/nginx.conf bind-mounted from a checkout on the host — and the deploy chain moves images and nothing else, so that config was a file the release could not deliver. A club merging a gateway fix got a new backend behind the old config, with every LAN member back in one rate-limit bucket, and a dashboard reporting a successful deploy. nginx/Dockerfile bakes it in. The deploy job used to refuse a stack that did not name the gateway image, or that still bind-mounted the file; with that job removed, whoever redeploys must check both by hand — neither mistake is visible any other way.

iot-build proves the flashing route

Beyond compiling court_mega, court_bridge and the simulator under PlatformIO and checking the simulator starts and binds, the job now runs make arduino-check — regenerate src/iot/court-box/arduino/ and fail on a diff — and then compiles both generated sketches with arduino-cli on the pinned cores (arduino:avr@1.8.6, esp8266:esp8266@3.1.2). Without it, a source change nobody re-exported leaves a technician flashing last week's firmware from a folder that looks current. It writes a throwaway secrets.h first: the real one is gitignored because it holds a WiFi password and the club key, and the four values only have to exist for the preprocessor.

e2e-device, no hardware

The real API from source against a fresh Postgres, the firmware's native simulator as the Mega half over TCP, a PayFast mountebank imposter, and test/e2e-device/scenario.py playing the ESP8266 bridge, the member's phone, the admin and PayFast. Every review finding it pins is printed as finding-id → assertion, and any failed assertion fails the job. Locally: make test-e2e-device.

The Portainer stack is a file — docker-compose.prod.yml

It is the stack verbatim: it pulls the three published images and carries every value inline, because a Portainer stack has no .env behind it and the founder's rule is that the file itself holds the minimum a running club needs. Four lines are marked CHANGE-ME and are edited once when the stack is created — database password, JWT secret, public hostname, mailbox password. Nothing else is configuration.

It publishes exactly one port, 8088. Cloudflared (outside the stack) dials it for members; the court box dials the same port on the machine's LAN address, which is what its secrets.h names. The stack keeps compose's own bridge rather than host networking, because the gateway reaches the API and the SPA by service name and because the API only believes X-Forwarded-* from that bridge's pinned subnet.

Names must be the ones the API reads

.NET maps Section__Key to Section:Key and nothing else. Until 2026-09-05 both compose files forwarded flat names — JWT_SECRET, APP_FRONTEND_URL, CORS_ALLOWED_ORIGINS, MEDIA_STORAGE_PATH — that no line of the API reads, while insisting on values for them: the API booted on the appsettings.json placeholders, dev JWT secret included. The three exceptions that genuinely take flat names, because their readers say so, are SMTP_* and the three WEBAUTHN_* keys. When adding a variable, find the Configuration[…] read first.

Trusted proxies and the hop count

Trust list127.0.0.1, ::1, and the pinned compose bridge 172.29.83.0/24. It used to be 172.16.0.0/12 — a million addresses, and on a club LAN inside that range every laptop was a trusted proxy able to forge its own client address.
A string, not an arrayLoad-bearing: .NET merges arrays by index, so with an array default, setting entry 0 left the rest trusted underneath — a deployment could add a proxy but never remove one. A scalar is replaced whole.
ForwardLimit 2One hop for the gateway, one for cloudflared. At the default of 1 the API stopped at cloudflared's bridge address and the entire remote membership shared one ten-a-minute auth bucket. Safe to raise because trust is re-checked at each hop.
X-Forwarded-Hostnginx forwards $http_host — host and port — because $host strips the port and the API composes absolute URLs (verification links, PayFast returns) from what it believes the request arrived on.
The onprem overlay is now a choice, not a requirement

docker-compose.onprem.yml existed because a UDP discovery listener needed the LAN's broadcast domain, which a docker bridge does not carry. There is no discovery any more, so what it still buys is hardening rather than connectivity: Postgres and MailHog bound to loopback instead of published, and Kestrel bound to loopback plus one address rather than every interface. The boxes are unaffected either way — :8088 is the address in their secrets.h and the only one this topology gives them.

Backups: nightly encrypted pg_dump offsite; the MASTER_SECRETS_ENCRYPTION_KEY that wraps tenant secrets lives in a password manager off the host, so losing the machine does not lose the keys. PayFast merchant credentials are per-tenant database settings, never environment. Biometric USB devices reach the container via --device passthrough, still commented out until a driver is chosen.

10Queued events do not survive a power cutAcceptedRAM ring; a court lit during an outage that ended at the breaker is never reported and sweeps as a no-show. Now honestly a not built rather than a cannot: the store's cap is 128 bytes and a 48-byte event would fit, but a half-right torn ring charges a member twice. The consequence changed direction with §6a and the entry has been corrected. It used to cost the member a penalty they did not earn — wrong, but visible on their own ledger and disputable. Under S5a the same booking is refunded in full and stamped peripheral_outage, so the club silently pays for a court that was played and nobody has a reason to complain. The loss is now the club's and it is not member-detectable; it shows up only as peripheral_outage refunds in the ledger and on booking.no_show. The mitigation that shipped with the correction is the alert copy: it no longer opens with "check its power", because a power-cycle is the one action that destroys the queued activations. Making the loss positively detectable is unbuilt, and the route this entry used to name does not work. It said a sequence gap after a reconnect would give it away, because the box persists its sequence mark and the API stores a DeviceEventReceipt per (device, seq). Both halves are true and the inference is not: EventQueue reserves sequence numbers 64 at a time to spare the flash, and begin() resumes at mark + 1 — past the whole reserved block, because "the previous boot may have issued any number inside that block, and there is no way to know which". So every reboot manufactures a gap of up to 63, whether or not a single event was lost, and a gap cannot tell "the queue lost N activations" from "the checkpoint skipped N numbers". Detecting this honestly needs something the box does not send today — a count of what it discarded, or a persisted ring. Accepted knowingly; item 7 makes it rarer.
