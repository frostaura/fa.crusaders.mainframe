Every path from a booking to a lit court

One box, four courts, no moving parts you have to babysit. Every flow the system runs, drawn lane by lane; what happens when the network is down; and how to put the whole thing in service with the Arduino IDE and one Docker command.

Bridge 2.2.2 · Mega 2.0.0 · one code per member · one API key · box polls, backend answers · wiring unchanged from Carl's schematic

How it works, in three sentences

Everything else on this page is a consequence of these.

Direction
The box calls. The backend answers.
The box runs no server and opens no port. It asks the backend on every scan and once a minute for its settings. Nothing ever needs to know the box's address.
Configuration
Desired state, rebuilt every minute.
Each heartbeat reply is a fresh snapshot: which court sits on which relay, what each button means, and the next two hours of bookings. The box replaces what it holds. A lost reply loses nothing.
Identity
One code per member, new every 30 seconds.
The member's My Code page shows one 19-character code, made on the phone with no signal, that opens the door, lights their own court or one they are a partner on, and pays for somebody else's. The backend checks both halves of it; offline the box checks the half it holds a key for and looks the member up among the players its roster names. Each code works once.

The flows

Every path the system runs, drawn as it happens: lanes are who acts, left to right is time. The coloured badge on each step names the project that implements it; the legend floats bottom-right. Click any step for the detail; the pills under a step are its possible outcomes.

Putting it in service

In this order. The backend first, because the box needs the API key the backend creates. Arduino IDE for both boards, Docker for everything else. Click a step for the settings; the full list is below the diagram.

  1. Prepare the server

    Any always-on machine on the club LAN. The box and the backend must be on the same network; the outside world comes in through Cloudflare.

    • Install Docker Desktop (Mac/Windows) or Docker Engine (Linux).
    • On the router, give this machine a DHCP reservation so its address never changes. Write the address down; it goes into the box in step 4.
    • Clone the repository, copy .env.example to .env, and fill in the values marked REPLACE_…: database password, JWT secret, encryption key, SMTP password. Set APP_PUBLIC_BASE_URL and the WebAuthn origin to your public address (step 3) once you have it.

  2. Start backend and frontend

    One compose file brings up Postgres, the API, the web app and the gateway that serves both on port 8088.

    docker compose up -d --build
    • Open http://<server-address>:8088 on the LAN. Create the admin account and the club (tenant); set windows and the default button map under Settings, and check the minute packages members will buy under Packages.
    • To update later: git pull then the same command. Data lives in a Docker volume and survives it.

  3. Publish it with Cloudflare (optional, for remote booking)

    Members book from home through a Cloudflare tunnel that points at port 8088. The box never uses it.

    • Run cloudflared on the same machine with one ingress rule: your hostname → http://localhost:8088.
    • Put that hostname into .env (APP_PUBLIC_BASE_URL, CORS_ALLOWED_ORIGINS, WEBAUTHN_ORIGIN, WEBAUTHN_RP_ID) and run the compose command again.

  4. Get the API key and write secrets.h

    The only four things the box ever needs to know.

    • In the web app, open Devices → Device API key → reveal → copy.
    • In the repository, copy src/iot/court-box/arduino/court_bridge/secrets.h.example to secrets.h in the same folder and fill in:
    #define WIFI_SSID       "ClubWiFi"
#define WIFI_PASSWORD   "…"
#define API_BASE_URL    "http://192.168.1.10:8088"   // the reserved address from step 1
#define DEVICE_API_KEY  "…"                           // from the Devices page

  5. Set up the Arduino IDE (once)

    Two board packages. No libraries to install; everything the sketches need ships inside their folders.

    • Install Arduino IDE 2.
    • Arduino AVR Boards is built in (for the Mega).
    • For the ESP8266: Settings → Additional boards manager URLs → add https://arduino.esp8266.com/stable/package_esp8266com_index.json, then Boards Manager → install esp8266 by ESP8266 Community.
    • Plug the box in over USB. No driver is needed on current macOS or Windows 10+; if no port ever appears, install the WCH CH34x driver.

  6. Flash the Mega

    The Mega does the physics: relays, buttons, scanner, LCD, and its own auto-off timer. It rarely changes.

    12345678
    Wait: that's the run position. For a Mega upload set
    12345678
    Mega upload: 3 and 4 ON, everything else OFF
    1. Open src/iot/court-box/arduino/court_mega/court_mega.ino.
    2. Board: Arduino Mega or Mega 2560, processor ATmega2560. Port: the USB serial port that appeared.
    3. Upload. Done when the IDE says so; the LCD shows the idle text.

  7. Flash the ESP8266 bridge

    The bridge is the brain: WiFi, the roster, every decision. This is the one you reflash when the WiFi password, the server address or the key changes.

    12345678
    ESP upload: 5, 6 and 7 ON, everything else OFF
    1. Open src/iot/court-box/arduino/court_bridge/court_bridge.ino (your secrets.h sits beside it; the build refuses to start without it).
    2. Board: Generic ESP8266 Module. Flash size 4MB (FS:2MB OTA:~1019KB). Upload speed 115200. Port: the same USB port.
    3. Upload. The LCD stays blank during this; that is expected.

  8. Run position, power cycle, verify

    12345678
    Run: 1 to 4 ON, everything else OFF, then power cycle
    1. Within a few seconds the glass shows CONNECTED SCAN TO START.
    2. Within a minute the box is on the Devices page as box-xxxxxx. Rename it; check that court 1 is on relay A and so on; save.
    3. Book a court a few minutes ahead on a phone, scan My Code at the box, watch the light. Press OFF. Check the wallet. The Devices page shows the bridge as 2.2.2; the Mega is never reflashed and stays 2.0.0.
Updating later

What you never do
Change a wire, a pin, a jumperThe schematic is fixed. Every fix is firmware or software.
Type anything into the boxIts whole configuration is the four lines and the Devices page.
Open a port or forward anything for the boxIt only ever calls out.

…and the doors

The same club, the same key, the same API — one small board per door instead of one per four courts. A member holds up the code their phone already shows them and the lock lets go for fifteen seconds. Nothing here touches a court, a booking or a balance.

The board
One ESP32, one lock, one lamp.
A QR scanner on a serial port, one relay on the lock, one LED. No screen and no buttons — the lamp is the whole of what a member sees. It calls out and never listens, exactly like the court box.
The image
One firmware for every door.
Nothing about a particular door is compiled in. You name the door in the web app; the board never learns its own name, so a spare board is simply a spare board.
The rule
A door is not attendance.
Walking in may mean collecting a racquet or watching someone else play. An open never checks anyone in, never reverses a no-show and never moves a minute of anyone's balance.

  1. Putting a door in service

    The server is already running and the club already has its key — a door needs nothing of its own. Steps 1 to 4 of the list above are done; this is everything else.

    • In src/iot/door-gate/arduino/door_gate/, copy the secrets.h.example that sits beside the .ino to secrets.h and fill in the same four values the box uses: WiFi name, WiFi password, http://<reserved-address>:8088, the club's Device API key. The build refuses to start without it and refuses an empty value in it. (The PlatformIO route reads its own copy under src/common/; both are gitignored.)
    • In the Arduino IDE install the esp32 core, exactly 2.0.17 — the sketch folder's own README carries the boards-manager URL. Only one version of a core installs at a time and 3.x is not a small difference.
    • Open src/iot/door-gate/arduino/door_gate/door_gate.ino, board ESP32 Dev Module, pick the port, Upload. No DIP positions to set and nothing to install from the Library Manager — the folder vendors every library it needs, and it is generated, so never hand-edit it.
    • Within a minute the door is on the Devices page by itself as gate-xxxxxx. Give it a name — "front-door", "side-door". Until you do, it works only while it can reach the server.
    • Under Settings, the three numbers a door runs on: how long the lock releases (15 seconds, anything from 1 to 30 — long enough to notice the lamp, move a bag and pull a handle, which three seconds was not), who may open a door (any active member, the default, or only members with a booking), and how early before a booking its holder may come in (30 minutes).

  2. What the lamp is telling you

    There is no screen. This is the entire user interface, and the last row is the one people report as a fault.

    LampMeaning
    SolidThe lock is released — push the door.
    Three fast blinksRefused. The door never says why: one refusal looks like every other from the doorway, deliberately.
    Slow blink, once a secondThe radio is not associated. The door is deciding from the bookings it already holds.
    Two quick blinksIt has just booted.
    Nothing at allA refusal while the door is already open. Solid outranks the blinks, so the second person of a pair sees a steady lamp — the door is open in front of them, which is the more useful thing for it to be saying. Not a dead LED.

  3. Before a door goes on a wall

    One paragraph, because it is the part of this page that is not software.

    None of this has ever run on hardware, and what a door does with no power has never been measured. The expectation is that it is released — but a power cut takes the lock's own supply with it, so the lock decides that one, and a dead board with the lock still powered is decided by how the lock is wired through the relay. Which lock is fitted and which relay contact feeds it are written down nowhere, so §12 of docs/go-live-checklist.md measures both with a meter and an audible lock instead of assuming: mains pulled, then board power pulled on its own; ten power cycles confirming the lock does not click on the way up, and the same after a watchdog reset; the backend unplugged at boot to prove the board sits quiet rather than reset-looping; a rostered member let in with the network down and an unrostered one refused; the roster left to go stale past six hours and confirmed to admit nobody; a door taken out of service and confirmed to refuse without falling back. And the one that is not ours at all: every door this board controls must open from the inside by pushing it — a panic bar, a handle — with no power, no relay and no firmware involved. Nothing here is a life-safety device.

What the glass is telling you

Every screen the box can show, and what it means.

The glass is four rows now, and no screen can get stuck on it
Four rows, not twoThe panel always was a 20×4; the firmware used to drive it as 16×2, so four columns of every line and two whole rows were unreachable. No wire changed — two build flags did. Row 0 is the title, row 1 the detail, row 2 the live state of the four courts, row 3 what to press plus a clock or a countdown. The zones never swap meaning, so you learn where to look once.
Fit a 1602 by mistake and it still readsRows 0 and 1, cut at column 16, are a complete sentence on every screen — never half of one. A smaller panel degrades to exactly the old behaviour rather than to nonsense. Somebody still has to look at the panel before a club box is flashed; that is on the go-live list.
Every screen expiresThe landing screen and the revert timer live on the Mega, for the same reason its lights-off timer does: the ESP is the half that goes away, and a timer that rescues you from a stuck screen is useless if it lives on the thing whose crash caused it. Every screen the bridge paints is an overlay with a deadline, clamped by the Mega into 1 to 120 seconds on the way in — so nothing can leave a refusal on the glass all evening with the buttons dead behind it, which is a failure this box has actually had.
Plain digits, no barThe countdown counts in numerals on purpose. A progress bar costs custom characters the display has to be given back after every bus hiccup, and tells you nothing the digits do not.
Press anything and the screen waits for youAny button press re-arms the screen you are reading, so nobody loses a half-made choice because they were still reading it. A press the box could not act on answers on row 3 alone and leaves the rest of the screen where it was.
